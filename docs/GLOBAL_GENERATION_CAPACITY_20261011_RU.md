# Общая ёмкость тяжёлой генерации

## Подтверждённая граница

`planner_state.claim_build_status` блокирует строку версии, а не всю систему.
`run_planner_build_worker._run_daemon` выбирает до max_jobs строк; этот параметр
не ограничивает другие процессы. В isolated PostgreSQL четыре разных задания
одновременно получили running. Общий лимит одной тяжёлой операции ещё отсутствует.

## Контракт реализации

На текущей машине общий лимит — 1; остальные задания сохраняются queued.
Ресурс занимает операция целиком, включая embeddings/scoring, MILP и проверку,
до сохранения результата либо terminal failure/cancel. Число worker-процессов
не может увеличить этот лимит. Конфликт ёмкости не является ошибкой программы.

Общее атомарное получение ресурса должно предшествовать version-row claim;
единый порядок блокировок исключает взаимную блокировку. Повторный вход
того же owner/job не занимает второй слот. Истёкшая аренда не разрешает
старому worker публиковать результат после захвата новым владельцем.
Освобождение — только точным владельцем; ошибочное освобождение чужой
операции запрещено. Отмена и восстановление сохраняют прежний активный план.

## Все тяжёлые входы

- Очередь daemon → build_plan: claim до вызова scoring уже есть, но он
  ограничивает только конкретную версию.
- planner_build.recompute_matches: отдельный claim перед scoring;
  при нехватке общей ёмкости нужен честный retryable ответ, не запуск модели.
- api/kag.py: прямые вызовы compute_all_matches также должны соблюдать ресурс.
- audit_cross_level_generation.py: scoring выполняется вне очереди перед
  построением плана; ограничение только daemon оставит этот путь незащищённым.

## Последовательность проверки

1. RED: два различных owner/job параллельно пытаются получить один слот;
   только один начинает тяжёлую работу, второй остаётся ожидающим.
2. GREEN: общий durable ресурс, конфигурация ёмкости и точная ownership.
3. Регрессии: повторный вход, cancel, crash/lease expiry, stale owner,
   сохранность прежних планов, порядок очереди, ошибки БД fail-closed.
4. Проверить API и CLI: scoring не начинается до допуска; прямой обход
   не должен оставаться ни в одном перечисленном входе.
5. Изолированный PostgreSQL multi-process контроль; затем controlled rollout
   при отсутствии активных пользовательских задач. Не менять старую историю.
6. Измерить очередь, wall time и peak RSS одной реальной генерации. Только
   затем повтор первых20 с новым отчётом; после независимой и содержательной
   приёмки — следующие40. Не объявлять throughput/cost измеренными по claims.

Это контракт следующей реализации, НЕ свидетельство готового ограничения.

## Проверка базового ограничителя

Добавлен generation_capacity.generation_slot: PostgreSQL session advisory lock
на отдельном соединении удерживается весь context. Проверены отказ busy до
входа в тяжёлый блок и освобождение при исключении. Дополнительный opt-in
test_generation_capacity_postgres выполнен в изолированной базе
curriculum_kag_restore_pilot_20261010: четыре отдельных соединения через
NullPool одновременно пытались получить слот; ровно одно admitted, три busy.
После освобождения новый запрос успешно вошёл. Каталог и планы не изменялись.
Три теста прошли через backend/venv/Scripts/python.exe, exit0.
Первый запуск системным Python не прошёл из-за отсутствия pydantic_settings;
это несовпадение окружения, не отказ PostgreSQL или ограничителя.

Пока отсутствуют интеграция со всеми входами, повторный вход owner/job,
автоматическая очередь и восстановление. Этот тест НЕ доказывает работу
нескольких пользовательских генераций, peak RSS, throughput или стоимость.

Дополнительно RED→GREEN проверен вложенный синхронный вход в том же thread
и с тем же Engine: scoring может использовать слот внешнего worker scope.
Выход внутреннего scope не освобождает внешний: конкурирующий thread на
реальном PostgreSQL остаётся busy. Этот helper нельзя держать через async
await; привязка здесь thread-local, не универсальная ownership задания.
Повторный запуск трёх тестов exit0. Подключение к продуктовым входам ещё
не выполнено, live API/worker не перезапускались.

Дополнительный реальный PostgreSQL тест: физическое соединение владельца
закрывается без advisory_unlock и без правки job leases; следующий scope
успешно получает ресурс. До закрытия другое соединение busy. Четыре теста
прошли, exit0. Это проверка потери DB-соединения, не падения всего worker
во время модели и не принятие пилота восстановления.

Ещё один вход: GET /coverage в api/kag.py при отсутствии сохранённых метрик
вызывает compute_all_matches и пишет MatchScore. Ограничения только POST
/match недостаточно. Обе функции async, но синхронная тяжёлая оценка вызывается
без offload. Интеграция должна исключить блокировку event loop и возвращать
retryable ответ при busy, не превращать его общим RuntimeError catch в500.
