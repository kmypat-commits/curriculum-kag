# Различающиеся стратегии A/B/C

Пользователь прямо подтвердил: B сравнивается с исходным планом вуза, не с A.
Это контракт реализации, а не заявление о готовой функции.

## Выявленное состояние

В PlanningProblem отсутствуют исходный состав и стратегия; solve_joint использует
одинаковую utility. Plan.variant_type содержит только A/B/C; ProjectVersion не
содержит выделенного неизменяемого исходного плана. Нельзя взять последний active
план и назвать его исходным: после генерации это результат самой системы.

## Цели оптимизации

- A: максимизировать взвешенную глубину доказанного покрытия РО. Для каждого РО
  учитывать максимум принятого evidence score выбранных дисциплин, а не сумму
  копирующих друг друга курсов. Вес берётся из LearningOutcome.weight; веса не
  усиливают evidence для прохождения admission.
- B: первым критерием минимизировать количество выбранных дисциплин, отсутствующих
  в подтверждённом исходном составе вуза. Вторым критерием максимизировать покрытие
  РО среди решений с найденным минимальным числом добавлений.
- C: компромисс между нормированным взвешенным покрытием и долей добавленных
  дисциплин. Нормировка фиксируется по доступному кандидатному набору и исходному
  составу, а не по найденным A/B. Коэффициент компромисса должен сохраняться в
  evidence результата, чтобы C можно было воспроизвести.

Для первой версии C используется фиксированный коэффициент0.5:
`0.5 * coverage - 0.5 * added_count / max(1, eligible_nonbaseline_count)`.
`coverage = sum(weight[lo] * max_verified_score[lo]) / sum(weight[lo])`,
score ограничен диапазоном0..1; при отсутствии принятых связей вклад РО равен0.
В знаменателе добавлений считаются уникальные допустимые nonbaseline Course.id
текущего frontier плюс фиксированные nonbaseline дисциплины; этот знаменатель
сохраняется в результате. Расширение frontier меняет задачу и её hash, поэтому
метрики двух разных frontier нельзя выдавать за одинаковые условия сравнения.
Для B сохраняются также необходимые fixed nonbaseline IDs: они дают постоянный
вклад в added_count, не скрываются из отчёта и не исключаются из расписания.

Количество новых Course в каталоге не является показателем B. Практика, ГОСО и
подтверждённые обязательные дисциплины остаются в жёстких правилах. Отсутствие
дисциплины в исходном составе не разрешает её удалить, если она обязательна.

## База сравнения

Нужен отдельный подтверждённый снимок исходного плана: project/version, источник,
original course codes и разрешённые внутренние Course.id, credits, content hashes,
source file SHA256, canonical SHA256, дата и подтверждающий пользователь. Коды
сопоставляются явно; не определять эквивалентность по похожему названию.

Снимок не заменяется после генерации или ручного редактирования результата.
Ссылка на загруженный файл без разрешённого состава не является готовой базой.
Пустой/несуществующий снимок для B/C возвращает baseline_missing; старая
опубликованная программа сохраняется. A остаётся доступным без исходного плана.
Доступ к снимку проверяется по владельцу проекта. Перенос между версиями должен
быть явным и сохранять provenance, не выбирать план другой версии автоматически.

## Различимость и диагностика

No-good cuts не заменяют разные цели. Если допустим единственный состав или
дальнейшая альтернатива нарушает ограничения, вернуть alternative_unavailable,
не сохранять дубль под новым названием и не внедрять чужие курсы ради отличия.
Сохранять objective version, baseline hash, LO weights, achieved coverage,
added IDs/count, solver bounds/optimality, frontier hash и причины отказа.

## Проверки реализации

1. На одном допустимом наборе A выбирает более сильное покрытие, B сохраняет
   исходный состав, C даёт объяснимый компромисс; одинаковые hard gates для всех.
2. Повторяющийся курс не удваивает покрытие; рост LO weight меняет целевую оценку,
   но не создаёт ложное admission evidence.
3. baseline_missing, чужой project, изменённый источник, неподтверждённое
   сопоставление и отсутствие альтернатив проверяются отдельно.
4. Подтверждённый required курс выбирается и при отсутствии в baseline.
5. Fresh20 затем40 на неизменных frozen входах с независимыми структурными и
   содержательными проверками; тренировочные данные не берутся из этой приёмки.

Открытый интерфейсный шаг: загрузка/подтверждение исходного плана и сохранение
снимка. До его реализации считать все имеющиеся A/B/C true-strategy готовыми нельзя.

## Solver B/C: первый проверенный этап

Четыре RED регрессии подтвердили: сравнение без baseline молча выполнялось,
а высокая generic utility вытесняла исходный курс в обоих режимах. Добавлен
baseline_course_ids; для явных B/C без непустой базы возвращается baseline_missing.
B минимизирует 2*added_variable_count-coverage: поскольку coverage лежит0..1,
целое добавление всегда важнее выигрыша покрытия. Fixed nonbaseline дают постоянный
вклад и не меняют оптимум; их фактический счётчик ещё требуется в publication evidence.
C использует согласованную0.5 нормировку, знаменатель union candidate/fixed IDs
вне baseline. Все41solver tests прошли; полный backend suite проверяется отдельно.
Это opt-in solver, НЕ live B/C: immutable подтверждённый baseline/API/UI ещё открыты.

## Приоритеты advisory и различающийся C

Новая RED регрессия выявила, что двухфазный preferred-block поиск переопределял
первый критерий B и добавлял курс3 вместо допустимого исходного1. Для явных B/C
эта advisory фаза больше не переопределяет согласованные objectives; required
course/block constraints неизменны. Первый edit попал в одноимённый if построения
строки, suite14046 показал ту же единственную ошибку; исправлена именно ветка
двухфазного поиска, строка restored. Отдельный реальный MILP пример подтверждает:
C выбирает более сильное покрытие, когда его выигрыш превышает нормированное
добавление; это characterization существующей формулы, не новый RED для неё.
