# Полный programme-level dataset EPVO — 25.08.2026

Полный экспорт выполнен из PostgreSQL shadow-базы без ограничения числа
программ. Артефакт находится вне Git в
`backend/.runtime/epvo-ranking-postgres-full/` и содержит `programs.jsonl`,
`course_lo_pairs.jsonl` и `manifest.json`.

Команда воспроизведения:

```powershell
$env:DATABASE_URL = "postgresql://curriculum_user:curriculum_pass@localhost:5433/curriculum_kag_shadow"
python backend/scripts/export_epvo_ranking_dataset_postgres.py `
  --database-url $env:DATABASE_URL `
  --output backend/.runtime/epvo-ranking-postgres-full `
  --max-programmes 0 `
  --min-labelled-links 1
```

Результат manifest:

| Показатель | Значение |
|---|---:|
| Программы | 11 017 |
| Train / validation / test | 7 706 / 1 650 / 1 661 |
| Строк course–LO | 833 022 |
| Положительные связи | 615 414 |
| Без экспертной оценки | 89 284 |
| Сильная экспертная оценка 1,0 | 468 852 |
| Средняя оценка 0,5 | 244 975 |
| Промежуточные оценки 0,25–0,8333 | 20 094 |

Оценки экспертов сохранены как непрерывная шкала, а не бинаризованы:
`0`, `0,5`, `1` и исторические промежуточные значения. Split назначается на
уровне программы, поэтому связи одной программы не попадают одновременно в
train и test.

Важно: прежние числа Recall@10 (например, 0,6099) относятся к отдельному
быстрому benchmark-срезу из 1 822 программ. Полный export теперь готов;
потоковый reranking benchmark выполнен без удержания 1,2 ГБ JSONL в памяти.
На 67 пригодных validation-программах/564 запросах streaming HashingTF-IDF с
train-only anchor дал Recall@10=0,5832; на 67 test-программах/562 запросах —
0,6098 (лучший anchor weight 0,35). MRR test составил 0,6380. Результат близок
к прежнему baseline и не даёт основания менять production reranker. Проверка
SBERT 40k на том же full split дала validation Recall@10=0,5829 и test
Recall@10=0,6137 для лучшего гибрида `0,5 SBERT + 0,25 lexical + 0,25 anchor`;
из-за отсутствия улучшения на validation модель не продвигается в production.

После этого benchmark был технически усилен: held-out программы теперь
обрабатываются по одной после завершения train-only статистик, а sparse
векторизация использует `float32`. Мини-тест на изолированном двухпрограммном
наборе прошёл; это снижает пиковое потребление памяти и не меняет split,
экспертные голоса или production-reranker. Полный пересчёт следует выполнять
отдельным длительным batch-job, а не во время запуска веб-приложения.

Дополнительная оптимизация сохраняет byte-offset выбранных held-out программ
при первом проходе JSONL и затем делает адресное чтение только этих строк.
Полный исходный файл больше не сканируется повторно на этапе оценки; это
снижает время I/O без изменения выборки, порядка хеш-селекции или leakage-safe
правила train-only статистик. Для длительного запуска можно передать
`--status-file backend/.runtime/epvo-ranking.status.json`: файл атомарно показывает
этап, обработанные программы и число запросов.

Если `--sbert-model` не передан, поля SBERT-гибрида в отчёте имеют значение
`null`, а не нулевые метрики: это означает «ветка не запускалась», а не
«качество равно нулю». Мини-срез из 40 train и 20 validation программ прошёл
через тот же конвейер и завершился статусом `complete` (83 запроса); полный
programme-level пересчёт остаётся отдельной длительной задачей.

Дополнительно выполнена проверка локализации текста. В RU-only режиме
векторизация и SBERT получают русские поля карточек дисциплин и РО, а не
объединённую многоязычную строку. На тех же programme-level split RU-only дал
на validation Recall@10=0,5914 (MRR=0,6589, nDCG@10=0,5599), а на независимом
test — Recall@10=0,6172 (MRR=0,6111, nDCG@10=0,5437) для смеси
`0,5 SBERT + 0,25 lexical + 0,25 anchor`. Улучшение небольшое и не достигает
целевого 0,80; это экспериментальный кандидат, production ranking не меняется.

В отдельном чистом срезе PostgreSQL (67 validation-программ, 585 запросов)
title-aware blend `0,45 lexical + 0,20 title + 0,35 anchor` дал Recall@10=0,4953
против 0,4847 у anchor-only; это небольшой (+0,0106) устойчивый прирост,
но он всё ещё ниже полного целевого порога 0,80 и потому не включён в production.
Word-level n-gram ветка на той же выборке дала Recall@10=0,4693, а смешанный
char/word/title вариант — 0,4824; оба хуже title-aware blend и оставлены как
отрицательный воспроизводимый эксперимент.

Проверена также отдельная graded-anchor ветка: вместо бинарного порога она
умножает anchor-сходство на силу экспертного голоса (0,5–1,0). На validation
полного split она дала Recall@10=0,5814 и MRR=0,6672 против Recall@10=0,5832
и MRR=0,6629 у обычного anchor weight 0,35. Из-за снижения Recall@10 ветка
отклонена до независимого test и в production не интегрирована.

### Проверка стабильности идентификаторов

Скрипт `backend/scripts/audit_epvo_id_overlap.py` отдельно проверяет, можно ли
без утечки использовать идентификаторы каталога как прямой prior. На полном
split точная пара `course_id–LO_id` не пересекается между train и held-out
(0,0%); пересечение только по `course_id` составляет 44,6% на validation и
45,3% на test, а по текстовому названию — 44,6% и 45,3% соответственно.
Следовательно, простое запоминание экспертных пар не решает задачу: следующий
безопасный эксперимент должен обобщать связь через семантические признаки и
programme-level контекст, а не подменять reranking lookup-таблицей.
