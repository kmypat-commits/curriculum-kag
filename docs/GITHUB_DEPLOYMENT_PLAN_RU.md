# GitHub и развёртывание — план без риска

## Текущее состояние

- Репозиторий очищен от старых `outputs`, архивных backup-наборов и промежуточной выгрузки ЕПВО: они перемещены в `archive/`, а не удалены.
- В Git сейчас есть один крупный рабочий файл: `backend/data/course_translations.json` (около 55,5 МБ). Это допустимо для локальной работы, но перед публикацией его лучше перевести в Git LFS или хранить как версионируемый релизный артефакт. Локальный `git-lfs` установлен (3.7.1), но файл пока не перевыставлялся в LFS автоматически.
- Файлы `.env` защищены pre-commit-проверкой и не должны публиковаться.
- PostgreSQL, SBERT-модели и сырые данные ЕПВО не следует включать в обычный Git-репозиторий: для них нужны backup/release-хранилище и контрольные суммы.

## Безопасная последовательность

1. Создать локальный коммит после просмотра `git diff` и прохождения `test.ps1`, frontend build и acceptance-test.
2. Создать приватный GitHub-репозиторий и отправить только код, миграции, документацию и маленькие конфигурационные примеры.
3. Большой JSON либо добавить через Git LFS, либо вынести в отдельный versioned dataset release. В GitHub нельзя отправлять `.env`, дампы PostgreSQL, `archive/`, кэш и веса моделей.
4. Для production разделить размещение: frontend можно публиковать на Vercel, backend с PostgreSQL/SBERT — на Docker-сервере или managed container-платформе. Vercel не должен запускать длительную генерацию учебного плана.
5. Supabase подключать только после отдельной миграции и smoke-теста; текущий PostgreSQL остаётся источником истины до подтверждения миграции.

## Что не делать автоматически

- не публиковать репозиторий без проверки секретов;
- не удалять archive и backup до успешного восстановления тестовой копии;
- не подключать MCP, который запускает постоянный индексатор и создаёт дубли процессов;
- не переносить тяжёлые модели и датасеты в Git без LFS/релизной политики.

## Аппаратные профили (следующий этап)

После стабилизации можно добавить `lite`, `balanced`, `quality`, `cuda` с ограничением batch-size, числа кандидатов и числа вариантов A/B/C. Профиль должен менять только параметры нагрузки, а не правила ГОСО и domain guard.
