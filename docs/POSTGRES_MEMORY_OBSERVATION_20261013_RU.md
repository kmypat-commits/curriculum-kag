# PostgreSQL: ограниченный замер памяти13октября

Это read-only наблюдение после завершённого контроля10251, не повтор параллельного
пилота и не доказательство причины его прежнего отказа.

В контейнере curriculum-kag-postgres-shadow cgroup memory.current=3509383168bytes.
memory.stat: anon11980800,file3486285824,kernel10145792,shmem146644992.
Shmem учитывается внутри file: показатели нельзя складывать как независимые.
inactive_file1306927104,active_file2032676864,file_dirty0,file_writeback0.
Docker stats показал2.047GiB: его показатель не тождественен memory.current.
Windows FreePhysicalMemory2477688KiB,TotalVisibleMemorySize14366200KiB.
Снимки сняты последовательно, а не одновременно; точное вычитание между ними
не является измерением причинного эффекта.

PG shared_buffers16384*8kB=128MiB,work_mem4096kB,
maintenance_work_mem65536kB,max_connections100. pg_stat_activity:
два idle подключения и одно active — сам диагностический SELECT.

В текущем состоянии доминирует файловый кеш, а не anon-память PostgreSQL.
Это не доказывает отсутствие будущих пиков work_mem, Python ORM или SBERT,
и не объясняет задним числом старый RAMguardpilot. Требуется временной ряд
anon/file/shmem/host_available и активных SQL/стадий во время следующего
разрешённого ограниченного пилота; caps не снижать для получения passing.
Конфигурация контейнера и базы не менялась, drop_caches/рестарт не выполнялись.

Практическое следствие: не оптимизировать импорты или SQL по одному vmmemRSS.
Следующий ресурсный дизайн должен учитывать cgroup-кеш и доступную память хоста,
с безопасным лимитом контейнера и откатом; до него тяжёлый пилот не повторяется.
