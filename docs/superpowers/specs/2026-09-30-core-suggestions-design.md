# Предложение профессионального ядра из цели и РО

Статус: дизайн для проверки. Расширяет согласованный необязательный контракт
2026-09-28-professional-core-design.md, раздел 10. Продуктовый код этого этапа
пока не изменён. Не заменяет десять пунктов общей цели.

## Результат для методиста

По отдельной кнопке система предлагает предметные блоки из цели и РО текущей
версии. Каждая карточка показывает: содержание блока, исходные фрагменты цели/РО,
реальные курсы-кандидаты, фрагменты их содержания и явно отмеченные пробелы.
Предложения не сохраняются и не включают режим требований автоматически.
Методист принимает выбранные карточки как preferred, проверяет содержание
кандидатов и при необходимости переводит блок в required существующим путём.

Нельзя считать ядром просто все РО подряд или список общих компетенций.
Для деревообработки общая цель «организация производства» не даёт права
предлагать металлургию как замену технологиям древесины.

## Сравнение подходов

1. По одному блоку на РО: легко проверяется, но размножает общие компетенции
   и не выделяет профиль. Отклонено.
2. Жёсткая таблица блоков по широкому домену: воспроизводима, но переносит
   прежнюю ошибку производственного домена в новый интерфейс. Отклонено.
3. Предметное структурированное предложение по конкретной цели и РО с
   проверяемыми ссылками на источник; поиск реальных кандидатов отдельно.
   Выбранный вариант. Содержательная релевантность проверяется контрастными
   примерами, не только валидностью JSON.

## Контракт предложения

- Только доступный пользователю проект, актуальная версия и read permission.
- Вход — снимок title, goal и всех lo_code/lo_text, а не общий domain1/domain2.
- Ответ связан с project_version_id, SHA256 канонического снимка входа,
  версией метода и моделью. Смена входа аннулирует предложение для принятия.
- Блок: title, description, lo_codes, source_excerpts, subject_scope.
  source_excerpts содержит точные фрагменты исходных полей с идентификаторами.
- Проверка ответа отклоняет неизвестные LO, отсутствующие/выдуманные цитаты,
  повторяющиеся блоки и превышение текущего лимита 12. Проверка цитаты сама
  по себе не доказывает предметную релевантность; UI сохраняет статус suggestion.
- Ориентир 4–8 блоков, но не искусственное заполнение до минимального числа.
  При слишком общем тексте — needs_profile_clarification с конкретным вопросом.
- Общие коммуникация/менеджмент/язык показываются отдельно как supporting,
  кроме случаев, когда они сами являются предметом программы (например,
  лингвистика или управление). Нельзя отбрасывать их по универсальному blacklist.

## Курсы и доказательства

Предложение блоков не имеет права создавать Course, подставлять course_id,
подтверждать соответствие или менять каталог. Реальные кандидаты извлекаются
существующим поиском и проверяются на текущие допуски уровня и scope.
Ранжирование учитывает description/topics/learning_outcomes, не только title.
Кандидат с одним названием помечается как недостаточно описанный.

Для кандидата сохраняются ID, доступный источник, поле, точный фрагмент,
content_hash, метод поиска и статус suggested. Полноту содержательного
покрытия подтверждает методист существующим server-issued механизмом.
Нет кандидатов в ограниченном поиске означает «не найдено в просмотренной
выборке», а не «курсов нет во всей базе». Показывать размер/границы поиска.

## Интеграция и сохранность

Использовать существующий CurriculumRequirements и preview/confirmation flow.
Принятие карточки добавляет её к черновику, не заменяет ручные блоки/required IDs.
Повторное принятие не создаёт дубль. Лимит 12 виден до сохранения, без тихой потери.
Принятый блок по умолчанию preferred, без подтверждённых курсов.
Сохранение через текущий endpoint с проверкой актуальности снимка предложения.
Старый опубликованный план и подтверждения других блоков не переписываются.
Существующие gates, frozen inputs и поведение A/B/C не ослабляются.

## Производительность и ошибки

Генерация предложений не входит в критический путь построения плана.
Один ограниченный запрос на действие, без вызова на каждый курс/checkbox.
Кэш привязан к входному hash и версии модели/метода. Поиск кандидатов привязан
также к ревизии каталога. Сохранять elapsed отдельно для предложения и поиска.
При недоступной модели/тайм-ауте ручной режим продолжает работать. Не выдавать
копию всех РО или фиктивные карточки за успешное предложение ядра.

## Приёмка перед включением

1. Контрастные неизменные входы: деревообработка/металлургия, история/общий
   менеджмент, филология/профессиональный язык, метрология/общие исследования,
   Web/общий IT. Профиль проверять по содержанию, а не одному слову в названии.
2. Общая или пустая цель/РО возвращает необходимость уточнения, не фантазию.
3. Общий курс не закрывает профиль автоматически; название без описания
   не получает подтверждение. Реальные разные языки/уровни не объединяются.
4. Чужой проект запрещён, устаревшая версия отвергается; принятие не стирает
   ручные требования и не меняет опубликованный план.
5. UI: запрос → просмотр источников → выбор → сохранение → существующее
   подтверждение → новое построение → покрытие/экспорт. Ошибка запроса
   не блокирует ручной режим.
6. Сравнение с базовым планом на том же входе, отдельный overlay требований:
   профильные блоки, чужие предметы, дубли, порядок, объём ручных правок.
   Не засчитывать overlay как неизменённый старый прогон 20→40.

До реализации нужны проверка этого дизайна и короткий план работ. Наличие
опционального ручного режима или зелёных технических тестов не закрывает
автоматическое предложение ядра и содержательную приёмку.
