# Контракт профессионального ядра и обязательных компонентов v1

Статус: проект для согласования, реализация не начата. Дата: 28.09.2026.

## 1. Цель и граница

Методист получает содержательно узнаваемую основу программы, а не только расписание с правильной суммой кредитов. Общие языковые, управленческие и исследовательские курсы не должны вытеснять профиль. Пользователь может зафиксировать конкретный курс или потребовать компетентностный блок. Отсутствие подходящих курсов показывается как пробел, не маскируется похожей общей дисциплиной.

Не обещаем вузовского утверждения, независимой экспертизы или 100% полноты при недостаточном каталоге. ГОСО, доступ, реальное LO-evidence, пререквизиты и нагрузка не ослабляются. Допуск240–244 только для target240/8; остальные длительности exact. Статью не менять.

## 2. Выбор подхода

- Только повысить similarity: дёшево, но общий LO снова может привести к чужому профилю.
- Все предложенные ИИ блоки сделать обязательными: риск ложных требований и новых отказов.
- **Выбран гибрид:** предложенное ядро улучшает приоритет подбора и выдаёт предупреждения; подтверждённые методистом обязательные требования становятся проверяемыми ограничениями. Обязательная нормативная часть остаётся существующей отдельной политикой.

Автоматическая карточка не является новым законодательным нормативом. Утверждение соответствия профилю отделено от технической валидности.

## 3. Типы требований

| Тип | Кто задаёт | Поведение |
|---|---|---|
| Нормативный компонент | Действующий ruleset выбранного профиля | Текущий обязательный gate; пользователь не отключает его этой формой. |
| Обязательный курс | Методист выбирает реальный Course.id | Курс включается целиком, с допущенной цепочкой предшественников; кредит/семестр не переписывается ради решения. |
| Обязательный блок | Методист подтверждает содержание и варианты покрытия | Один или несколько подходящих реальных курсов должны выполнить критерий блока. |
| Предпочтительный блок | Автоматическое предложение или выбор методиста | Приоритет при подборе; при пробеле сохраняется честное предупреждение. |

«Обязательный» означает обязательный в этом запросе, а не обязательный для всех вузов. Обычная галочка «не учитывать ограничения» не вводится.

## 4. Входной контракт

В типизированные constraints текущего проекта добавить объект `curriculum_requirements`, schema_version=1. Сохранять через существующий механизм изменения условий/версии; не вводить второй редактор.

- `required_course_ids`: уникальные положительные внутренние `Course.id`, максимум30. В UI отображать также внешний `Course.course_id`; никогда не путать эти ID.
- `core_blocks`: максимум12 блоков. Каждый: стабильный `id`, `title`, `description`, `lo_codes`, `requirement` (`preferred`/`required`), `origin` (`system_suggestion`/`methodist`), `min_courses` (1–5), `min_credits` (целое≥0), `accepted_course_ids`, `confirmation`.
- `confirmation`: author_user_id, timestamp, rationale; записывает сервер после проверки полномочий. Клиент не может подставить чужого автора или статус approved.
- Системная рекомендация по умолчанию создаёт4–8 кратких блоков; это UX ориентир, не обязательное число блоков для всех направлений. Если исходный текст недостаточен, показывать «нужно уточнить профиль», не выдумывать карточку.

Required-блок должен иметь подтверждённое описание и допустимые реальные варианты покрытия; пустой список вариантов допускается как сохранённое требование, но preflight явно сообщает отсутствие покрытия. `min_courses` и `min_credits` применяются одновременно. Система не назначает автоматически универсальную долю профильных кредитов.

`accepted_course_ids` — выбор/подтверждение соответствия блоку, а не обход технического допуска. Недопустимые по уровню, scope, evidence или prerequisite курсы не становятся допустимыми из-за подтверждения.

## 5. Доказательства покрытия

Для каждого предложенного соответствия «блок—курс» сохранять course_id, block_id, source_reference, source_revision, content_hash, source_field, подтверждающий фрагмент, метод поиска и статус (`suggested`/`confirmed`/`rejected`). Статус решения относится к конкретному проекту/версии профиля; глобальный каталог не переписывать.

Подтверждение по одному названию не считать доказательством глубины. Источники: существующие Course.description/topics/learning_outcomes/assessment_methods и доступные исходные материалы ЕПВО. Семантическая близость помогает найти кандидата, но не превращается в экспертное подтверждение. AI не создаёт фиктивную оценку, текст источника или ручную подпись.

Общая компетенция управления не автоматически закрывает разработку сайтов, деревообработку или метрологию. Курс может поддерживать несколько блоков, но общая сумма кредитов плана считается один раз. Пер-блоковые кредиты показываются как поддерживающие и **не складываются** в уникальную долю профессионального ядра. Уникальные профильные кредиты считать по объединению course_id.

## 6. Freeze, изменение и совместимость

Требования и подтверждения входят в frozen ProgramSpec/request hash вместе с текущей моделью правил; revision и evidence-хэши сохраняются в результате. Изменение требований во время сборки создаёт новую версию/запрос, не меняет работающий build. Retry прежней попытки использует прежний снимок.

Изменение текста блока аннулирует прежние подтверждения этого блока. Изменение содержимого курса относительно content_hash требует повторной проверки соответствия; исторический план и объяснение остаются неизменными.

Legacy-проект без нового объекта сохраняет существующий технический путь. Карточку профиля предложить без незаметного введения новых hard-ограничений; отсутствие проверки явно показать. Не требовать повторного подтверждения каждого курса для запуска обычного черновика.

## 7. Preflight до дорогого solver

Проверить существование/доступность ID, LO-коды, диапазоны требований, конфликт обязательных эквивалентных версий, допустимость уровня/домена, доступные варианты блоков, цепочки предшественников и необходимые кредитные нижние границы.

Вернуть для каждого требования: доступные кандидаты, исключённые ID и причины, необходимый минимум, предупреждения. Возможные reason codes:

`required_course_missing`, `required_course_not_admissible`, `required_equivalent_courses_conflict`, `core_block_has_no_admitted_candidate`, `required_closure_credit_lower_bound`, `requirements_changed`, `evidence_revision_changed`.

Неполный shortlist не доказывает отсутствие во всём каталоге. До финального отказа расширить поиск конкретного дефицитного блока в рамках существующих bounded frontier budgets; в отчёте указать охват поиска. Только доказанный необходимый конфликт позволяет ранний отказ; таймлимит означает «не найдено за бюджет», не «невозможно».

## 8. Подбор и MILP

Расширить существующие `PlanningProblem` и frontier, не создавать второй solver:

1. Обязательные ID и подтверждённые варианты required-блоков не терять из-за top-N общего рейтинга. При ограничении frontier показывать неполноту, а не молча исключать требования. Зависимости добавляются существующим chain-admission.
2. Для обязательного курса `x_course=1`, если он не включён в fixed_schedule. Fixed-курс может закрывать блок только при подтверждённом соответствии, а не по своему нормативному статусу.
3. Для required-блока на подтверждённых допустимых кандидатах: число выбранных≥min_courses и поддерживающие кредиты≥min_credits, с учётом уже фиксированных курсов. Уникальность дисциплин действует одновременно. Избыточно требуемая цепочка не игнорируется.
4. Для preferred-блоков лексикографический приоритет: сначала закрыть больше различных профильных блоков, затем действующий рейтинг. Реализовать ограниченный двухпроходный objective в одном time budget; остаток бюджета и feasible incumbent явно отражать. Кредитные и LO-gates остаются hard. Не наращивать similarity за фиктивный evidence.
5. Не удалять «лишние» курсы после решения. Любая ручная замена вызывает повторную структурную и блоковую проверку.

Этот контракт не требует fuzzy-слияния всех похожих предметов. Проверенные группы эквивалентности остаются отдельным механизмом, языковые уровни и разные темы сохраняются.

## 9. Результат и интерфейс

В результат добавить `core_coverage`: block_id, requirement, status (`covered`/`gap`/`unconfirmed`), selected_course_ids, supported_credits, подтверждения и причины. Добавить `required_courses`: requested/included/missing IDs с объяснениями. Хранить в snapshot/metrics, читать одинаково в UI и экспорте.

Перед кнопкой генерации — компактная секция «Что обязательно включить»: поиск реального курса, карточки блоков, галочка обязательности, показ источника требования. Нормативные компоненты отдельно read-only. Открытый выбор не запускает LLM на каждое переключение.

Статусы разделены:

- Технически валидный + выполнены required-требования: обычный результат; отдельная пометка предметной проверки.
- Пробел preferred-блока: доступный рабочий черновик с предупреждением, без утверждения полной профильной готовности.
- Не выполнено required-требование: не публиковать как проверенный результат; сохранить диагностику/доступный черновик существующим безопасным draft-путём. Старый активный план сохранить.
- Cancel/infra-error: не превращать в успешный draft.

Для legacy результатов карточка покрытия может быть реконструирована, но это прямо обозначается. Новое объяснение не приписывать старому solver.

## 10. Производительность и предел первой версии

Не вызывать внешнюю LLM для каждого курса на критическом пути. Предложения блоков можно подготовить до build один раз и кешировать по spec/catalog/model hashes; отсутствие LLM не ломает ручной режим. Описание и доказательства кандидатов загружать пачкой. Проверку блоков повторно использовать в preflight/solver/read-only verifier через единый immutable DTO.

Двухпроходный objective требует замера; общий timeout не повышать вместо ускорения. Точный цельный SLA не объявлять до before/after. Автоматическую генерацию блоков и их качественные шаблоны вводить как отдельный шаг после работающего явного контракта, без исключений по programme_id.

## 11. Приёмка

TDD-контрпримеры: профильный курс проигрывал общему по рейтингу; общий курс не подтверждает профильный блок; обязательный курс теряется из frontier; required-блок не покрыт; fixed-курс учтён дважды; два обязательных эквивалента; цепочка не помещается; изменение evidence; неизвестный ID; чужая версия/подпись; frozen retry и изменение условий.

Проверить интерфейс «выбрать→генерировать→reload→увидеть подтверждения→экспорт», legacy без новых требований, отмену и сохранение прежнего плана. Сначала контроли истории/филологии/метрологии/Web/деревообработки/IT-медицины, затем прежние20→40. Исходный frozen manifest не менять. Новые требования для экспериментального контроля фиксировать отдельным overlay manifest/hash и явно сравнивать режимы, не засчитывать изменённые входы как старую неизменённую приёмку.

Критерии: все required-требования выполнены либо честно диагностированы; preferred-покрытие не скрыто; ноль фиктивных подтверждений; технические gates сохранены; состав лучше удерживает заявленный профиль по проверяемым материалам. Независимая техническая проверка не заменяет предметную оценку.
