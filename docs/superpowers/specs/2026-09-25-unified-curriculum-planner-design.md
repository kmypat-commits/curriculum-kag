# Unified curriculum planning: design

## Purpose and scope

Curriculum-KAG must produce a defensible variant A from a programme goal and learning outcomes without silently losing a required outcome, discipline, prerequisite, or semester constraint at a later repair stage. This is for methodologists reviewing a proposed curriculum, not a claim that an unreviewed AI-generated curriculum is ready for accreditation. The same planning contract will support optional variants B/C; the first acceptance target is the existing fixed cohort of 20 real programmes, then the next 40 disjoint programmes. Input identities and quality gates must not change to improve the reported pass rate.

The last complete first-20 run passed 16 and failed four programmes: 21992, 15705, 20787, and 14547. The current separate selector, ГОСО merge, exact-credit fitter, LO repairs, prerequisite repairs, and schedule repairs can undo one another. In 21992 the selector included course 2422 with ON1 evidence, but the ГОСО merge correctly removed it as a redundant general foundation. Domain-relevant alternatives for ON1 require prerequisite chains not selected together. In 15705 the selected set has no valid schedule within the current semester windows. The 20787 and 14547 failures include insufficient real-course LO evidence. These observations motivate one feasibility contract, not exceptions keyed to those four IDs.

## Selected approach and alternatives

Use a single deterministic, bounded mixed-integer optimization pass that selects real courses **and** assigns their semesters together after retrieving a candidate frontier and the mandatory ГОСО block. It should reuse the repository's SciPy MILP dependency, raw semantic/expert evidence, scoped EPVO data, semester rules, and independent final verifier. Hard constraints are constraints of the optimization, never objective penalties.

Adding another LO-repair loop after ГОСО is faster to code but leaves later trimming and scheduling able to invalidate it. Replacing the entire catalogue retrieval, scoring, and verifier would be broader than needed and risks losing already-tested behaviour. The new assembly boundary therefore replaces the competing late selection/repair decisions while leaving retrieval, evidence calculation, ГОСО definitions, and the independent verifier authoritative.

## Component boundaries

1. **Candidate frontier** reads a project version and already-computed MatchScore/EPVO records. It returns deterministic, admissible real-course candidates with stable IDs, credits, education-level and domain/scope provenance, raw semantic and expert evidence by LO, prerequisite IDs, recommended and allowed semesters. It includes the prerequisite closure of every retained candidate and removes ГОСО duplicates *before* counting LO coverage. A candidate whose required prerequisite cannot itself be admitted is excluded with a recorded reason. Start from the existing scored/selected candidates plus top in-scope alternatives per uncovered LO; widen deterministically when no solution is found. A bounded frontier is never presented as proof that the whole catalogue has no solution.
2. **Regulatory block** comes from the existing ГОСО definition. Its courses, credits, and semesters are fixed in the model. The same duplicate rule that excludes general foundation cards from the final plan applies when building the frontier, so a course cannot satisfy an LO only to disappear during ГОСО merge.
3. **Joint assembler** owns binary course-selection and course-semester variables. It selects a whole prerequisite chain, enforces an earlier semester for each prerequisite, exact credit bounds, every semester's load bounds, education-level/scope admission, domain quotas, credible real-course evidence for every professional LO, per-course direct LO evidence (or explicitly admitted structural prerequisite), mandatory competency blocks, and the existing bridge budget. The meaning and values of these rules come from the current verifier and project constraints; the assembler does not lower thresholds. For the frozen real cohort, it does not invent disciplines or use a synthetic bridge to claim real-course LO coverage.
4. **Objective and alternatives** operate only inside the feasible region: prefer stronger raw/expert LO evidence, exact EPVO scope, and pedagogically appropriate placement, then fewer synthetic modules and less redundancy. Variant A is deterministic. B/C use the same hard constraints and a diversity objective relative to A; they are computed only when requested. A different seed or scoring preference must never alter admissibility.
5. **Publication boundary** calls the existing independent `verify_curriculum_plan` on the actual proposed schedule. Only a feasible, quality-passing schedule is published atomically. The old active plan remains untouched when no verified replacement exists. A verifier disagreement is a defect/diagnostic, not permission to waive a gate. Each attempt records candidate-frontier version/hash, solver status and elapsed time, actual constraint failures, and output fingerprint.

## Mathematical contract

For every admissible real course `c`, `x[c]` is binary; `y[c,s]` is binary only for allowed semesters. `sum_s y[c,s] = x[c]`. For each prerequisite `p -> c`, `x[c] <= x[p]` and `y[c,s] <= sum_{t<s} y[p,t]`. Mandatory ГОСО items are fixed at their required semesters. For every semester, fixed ГОСО credits plus `sum_c credits[c] * y[c,s]` must be within the verifier's permitted load bounds, including its explicit regulatory rules. Total credits must be between the project's target and target plus its configured tolerance. Domain contributions use the verifier's scope/share semantics; a different single-domain label shortcut is not acceptable. For every professional LO, at least one selected real course must have the verifier-recognised semantic/expert evidence at or above its existing real-course threshold; every selected non-regulatory course must satisfy the existing direct-evidence or structural-prerequisite contract. Bridge count and allowed bridge types follow existing project policy.

The feasible region must also respect source semester and foundation windows, education level, excluded courses, required competency blocks, and confirmed replacements. Constraints that cannot be expressed exactly in the first MILP version remain checked by the independent verifier; a rejected candidate produces a diagnostic and a deterministic exclusion cut for a bounded retry, never a published plan. If a feature's verifier semantics cannot be represented safely, keep the old plan and report that limitation rather than claim success.

## Failure and performance behaviour

Distinguish `infeasible_with_complete_frontier`, `no_solution_in_bounded_frontier`, `solver_timeout`, `invalid_candidate_data`, and `verifier_rejected`. Report affected LOs, prerequisite closures, credit/load bottlenecks, and scope reasons where evidence supports them. Do not call a timeout or truncated frontier globally infeasible. No generic “Не удалось сформировать план” when a specific failure is known.

The optimizer uses deterministic course ordering, a measured time budget, and progressive frontier widening. Record retrieval, frontier, solve, and verification durations. A timeout yields an explicit retryable state and leaves the old plan intact. The initial release must compare wall-clock time and memory against the same frozen cases; it must not replace an honest failure with a 30-minute silent wait. GPU availability does not change the mathematical feasibility contract.

## Validation and rollout

Write red-first unit tests for prerequisite closure, ГОСО duplicate removal before LO accounting, raw evidence threshold, semester windows, credits, quotas, and an infeasible selected set with a feasible alternative. Test that the four known failures are not special-cased. Test a verifier disagreement, timeout, and retained old plan. Run the full backend suite before the cohort.

Then run each of 21992, 15705, 20787, and 14547 from the unchanged input files as focused regressions. Re-run **all of the same first 20 programmes from offset 0** into a new report. At any failure, retain reports, fix the general cause, and restart that entire 20-case run. Only after 20/20 internal gate and a separate independent check of exact manifest identity, prerequisites, actual total/semester credits, source-file SHA256 and canonical output hashes may the next 40 disjoint programmes (offset 20) start. No old 50+30/80 batch substitutes for this sequence. A passed internal gate is not independent expert review. Article and reviewer responses may use only verified outcomes and must distinguish generated plans from expert judgements.

## Non-goals

No relaxation of ГОСО, LO, credit, semester, domain, or prerequisite requirements to raise a pass count. No catalogue-card fabrication, replacement of frozen input programmes, migration of storage, redesign of the UI, or blanket refactor of unrelated planner modules. If strict constraints reveal a genuine data deficiency, retain an auditable failure and request expert catalogue/LO correction separately.
