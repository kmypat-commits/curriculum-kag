## Что ещё не закрыто

### 1. Междисциплинарные квоты и старые проекты

Свежие раздельные контроли «IT + Здравоохранение» (бакалавриат, ГОСО РК, 240 кредитов) после расширения вторичного retrieval и общего bridge-бюджета дали 240/240 кредитов и 0 жёстких нарушений во всех A/B/C; bridge 3/4/3, международный score 100/85,7/100. Это закрывает ранее наблюдавшийся дефект квоты на новом запуске и честно показывает остаточную потребность в bridge.

Старый проект 135 намеренно не объявляется качественным до завершения отдельного прогона: его legacy-пул содержит повреждённые тексты и недостаточно допустимых real-course кандидатов. Система больше не маскирует дефицит дополнительными мостиками. Для него требуется пересборка из нормализованного EPVO-репозитория или подтверждение направления, а не ослабление проверок.

Контроль проекта 16 («Киберследователь») после исправления фильтра медицинских специальностей дал 240/240 и hard-нарушения 0 во всех A/B/C; все три варианта прошли проверку качества и ГОСО, без семестровых/уровневых нарушений. Bridge-модулей осталось 4/5/4, поэтому международный quality-score вариантов с пятью мостиками снижается до 85,7: это предупреждение для экспертного выбора, а не скрытая подмена реальными дисциплинами.

### 4. Инфраструктурные остатки

- Alembic уже содержит две миграции и применяется на чистой PostgreSQL-БД; следующая миграция нужна только для новых изменений схемы.
- PostgreSQL endpoint-контракты: 6/6 локально и включены в CI через сервис `pgvector/pgvector:pg16`.
- В production-коде осталось 32 широких `except Exception`; optional AI и localization fallback уже переведены на конкретные типы ошибок, остальные места требуют поэтапного сужения.
- Модельный каталог содержит 24 директории; безопасный manifest выделяет 38 кандидатов к архивированию/удалению после резервной копии, потенциально 45,733 GB. Удаление в этом аудите не выполнялось.
- Ранжирование остаётся исследовательским: лучший Recall@10 0,7071; целевой порог 0,80 пока не достигнут, поэтому reranker не внедрён.
- Пересчёт метрик выполнен воспроизводимо командой `recalculate_plan_metrics.py --all --apply`: 18 версий, 54 плана, все `metrics_schema_version=2`, без изменения кредитов и состава курсов.
- Временные проекты с префиксом `AUTOTEST` удалены после контроля; пользовательские проекты и планы не затрагивались.

Это не дефект приложения, но эти каталоги нельзя включать в Git или контейнер релиза целиком. Модели и резервные копии должны поставляться отдельными артефактами с manifest/checksum; `venv` и кэши — пересоздаваться из lock-файлов.

Текущий аудит подтверждает работоспособность тестового, PostgreSQL и production-build контуров. Проект 16 и новые контрольные профили закрыты; незавершёнными остаются углубление Alembic-схемы, разбиение оставшихся крупных модулей, пересборка устаревшего проекта 135 и reranking. PostgreSQL endpoint smoke-тест на отдельной `_test` базе пройден 6/6. Поэтому система готова к контролируемому staging, но ещё не к безусловному production-релизу.

## План оптимизации после аудита

1. **Безопасность качества:** запретить активацию варианта с `quality_passed=false`; добавить в UI явное объяснение и кнопку пересборки только проблемного варианта. Ремонтировать B/C проекта 16 через общую semester-repair стратегию, не ручные правки.
2. **Legacy-путь:** для проекта 135 запускать диагностическую пересборку после выбора корректного EPVO-направления; при повреждённых текстах останавливать генерацию с понятной причиной вместо искусственного заполнения bridge.
3. **Рефакторинг:** разделить `variant_strategy.py` на retrieval/ranking/assembly и `PlanBuilder.jsx` на quality/bridge/LO-панели, сохранив фасады и контрактные тесты.
4. **Производительность:** кэшировать EPVO/LO-индексацию по checksum, перенести progress генерации в PostgreSQL, снять p50/p95 для API и страниц.
5. **Reranking:** восстановить полный frozen programme-level dataset, обучить hard-negative/listwise вариант с EPVO expert score, уровнем и семестром; внедрять только при Recall@10 не ниже baseline и целевого 0,80.
6. **Релиз:** добавить Alembic-проверку в CI, lock-файлы Python/Node, manifest моделей/данных и staging smoke-тесты RU/KK/EN перед Git tag.

## Ограничения аудита

Снижение квоты или признание bridge реальной дисциплиной не допускается: это улучшило бы цифру, но исказило бы качество. Порог «90–100%» можно заявлять только после независимого прогона с сохранёнными отчётами и экспертной верификацией.
