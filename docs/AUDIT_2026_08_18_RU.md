## Что ещё не закрыто

### 1. Междисциплинарные квоты и старые проекты

Свежие раздельные контроли «IT + Здравоохранение» (бакалавриат, ГОСО РК, 240 кредитов) после расширения вторичного retrieval и общего bridge-бюджета дали 240/240 кредитов и 0 жёстких нарушений во всех A/B/C; bridge 3/4/3, международный score 100/85,7/100. Это закрывает ранее наблюдавшийся дефект квоты на новом запуске и честно показывает остаточную потребность в bridge.

Проект 135 повторно проверен после расширения scoped-кандидатов и восстановления точного EPVO-пула. Он всё ещё честно отклоняется: 172/240 кредитов, 5 bridge, 8 hard-нарушений и одинаковые A/B/C. Причина подтверждена данными: для шести профессиональных LO есть только 27 дисциплин с effective score >= 0,4 (85 кредитов), а по второму направлению — 7 дисциплин (31 кредит); этого недостаточно для 40/40 квот при hard bridge-limit. Алгоритм теперь не маскирует дефицит и должен направлять проект на пересчёт LO-связей/экспертное подтверждение, а не выдавать ложный план.

Контроль проекта 16 («Киберследователь») после исправления фильтра медицинских специальностей дал 240/240 и hard-нарушения 0 во всех A/B/C; все три варианта прошли проверку качества и ГОСО, без семестровых/уровневых нарушений. Bridge-модулей осталось 4/5/4, поэтому международный quality-score вариантов с пятью мостиками снижается до 85,7: это предупреждение для экспертного выбора, а не скрытая подмена реальными дисциплинами.

### 4. Инфраструктурные остатки

- Alembic уже содержит две миграции и применяется на чистой PostgreSQL-БД; следующая миграция нужна только для новых изменений схемы.
- PostgreSQL endpoint-контракты: 6/6 локально и включены в CI через сервис `pgvector/pgvector:pg16`; CI дополнительно проверяет Alembic head и изолированный `pg_dump`/`pg_restore` round-trip.
- В production-коде осталось 8 широких `except Exception`; API KAG, health-check, bcrypt, graph vector conversion, bridge-commit и embedding/ranker loading уже сужены до ожидаемых типов ошибок. Оставшиеся места относятся к отказоустойчивому LLM-провайдеру и транзакционным границам planner/repository; их нельзя механически заменить одним типом без потери fallback-поведения.
- Модельный каталог содержит 24 директории; безопасный manifest выделяет 38 кандидатов к архивированию/удалению после резервной копии, потенциально 45,733 GB. Удаление в этом аудите не выполнялось.
- Public-release gate проверил 440 отслеживаемых файлов; модели, базы и датасеты намеренно не публикуются автоматически.
- Ранжирование остаётся исследовательским: после восстановления полного candidate pool (все курсы программы, а не только положительные пары) независимый прогон на 80 test-программах/629 LO-запросах дал Recall@10=0,4737, MRR=0,4106, nDCG@10=0,3702. Исторический 0,7071 получен на положительных парах и не используется как сопоставимый baseline. Целевой Recall@10 0,80 пока не достигнут, поэтому reranker не внедрён.
- Полный v3 programme-level export содержит 1 819 программ (1 288/273/258), но прежний `course_lo_pairs.jsonl` был неполным: в нём отсутствовали тексты курса и РО. Новый экспорт сохраняет `course_title`, `course_description`, `lo_text` и градуированный `expert_score`; benchmark теперь автоматически подхватывает соседний `programs.jsonl`, сохраняет все курсы-кандидаты и останавливается с диагностикой до вычисления метрик на пустом артефакте.
- Контрольный прогон на старом неполном артефакте (258 test-программ) дал 0,622 Recall@10 и признан диагностическим, не модельным результатом. Текстово-полный candidate-pool benchmark уже выполнен локально; после запуска PostgreSQL его нужно повторить из актуального raw-слоя, чтобы исключить устаревшие данные.
- Stage-cache теперь учитывает упорядоченный digest EPVO checksum/fingerprint в PostgreSQL и инвалидирует cache-hit после in-place исправления исходных записей; в SQLite оставлен детерминированный min/max fallback для локальных тестов.
- Пересчёт метрик выполнен воспроизводимо командой `recalculate_plan_metrics.py --all --apply`: 18 версий, 54 плана, все `metrics_schema_version=2`, без изменения кредитов и состава курсов.
- Временные проекты с префиксом `AUTOTEST` удалены после контроля; пользовательские проекты и планы не затрагивались.

## План оптимизации после аудита

1. **Безопасность качества:** запретить активацию варианта с `quality_passed=false`; добавить в UI явное объяснение и кнопку пересборки только проблемного варианта. Ремонтировать B/C проекта 16 через общую semester-repair стратегию, не ручные правки. Перед запуском вариантов уже работает `evidence_preflight.py`: дефицит профессиональных EPVO/LO-связей возвращается как `422`.
2. **Legacy-путь:** для проекта 135 запускать диагностическую пересборку после выбора корректного EPVO-направления; при повреждённых текстах останавливать генерацию с понятной причиной вместо искусственного заполнения bridge.
3. **Рефакторинг:** завершить разбиение `variant_strategy.py` на retrieval/ranking/assembly и оставшихся planner-модулей; quality-панель `PlanBuilder` и router course flags уже вынесены, фасады и контрактные тесты сохраняются.
4. **Производительность:** кэшировать EPVO/LO-индексацию по checksum, перенести progress генерации в PostgreSQL, снять p50/p95 для API и страниц.
5. **Reranking:** восстановить полный frozen programme-level dataset, обучить hard-negative/listwise вариант с EPVO expert score, уровнем и семестром; внедрять только при Recall@10 не ниже baseline и целевого 0,80.
6. **Релиз:** Alembic-проверка добавлена в PostgreSQL CI; прямые Python-зависимости зафиксированы в `backend/requirements.lock`, Node-зависимости — в `frontend/package-lock.json`. Остались manifest моделей/данных и staging smoke-тесты RU/KK/EN перед Git tag.

## Ограничения аудита
