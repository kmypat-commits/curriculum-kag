# Инструкции исполнителям: запуск Curriculum-KAG для методистов

Основание: [06_READINESS_FOR_METHODISTS_RU.md](06_READINESS_FOR_METHODISTS_RU.md), проверка 13.09.2026. Это задания для реализации, а не отчёт о выполненных доработках. Рабочий каталог: `D:\curriculum-kag\curriculum-kag`.

## 1. Какую модель и режим выбирать

Мой базовый выбор для экономной разработки — **GPT-5.6 Terra / medium**. Для изменений solver, evidence, транзакций и очереди — **GPT-5.6 Sol / high**. Если нужна одна модель на весь список — Sol / medium, повышая до high для отмеченных задач. **Low недостаточно для всего проекта**: он подходит узким правкам текста/вёрстки с готовыми требованиями.

Luna / medium можно давать небольшие интерфейсные задачи, тестовые данные и документацию после фиксации контракта. Независимый разбор сложной архитектуры и итоговую проверку результата имеет смысл поручать Astra / high точечно. Не держать max постоянно и не отдавать слабой модели весь монолит «исправь всё»: выигрыш от меньшей цены может исчезнуть из-за повторных ошибок.

Это инженерная рекомендация по риску задачи, не опубликованный сравнительный benchmark на этом репозитории. В официальной документации Terra позиционируется как баланс возможностей и цены, Sol — для сложной профессиональной работы, Luna — для задач с ограниченным бюджетом. Названия доступны в текущем контексте Codex; стоимость/списание подписки не выводятся из API-цен. Источники: [Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol), [Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna). OpenAI рекомендует повышать effort по измеренному улучшению качества, а не автоматически: [руководство](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.5).

| Тип работы | Практический выбор | Проверка результата |
|---|---|---|
| Тексты, подписи, одна небольшая UI-форма | Luna medium / Terra low | Локальный тест и просмотр интерфейса |
| PDF, read-model, форматирование экспорта по готовому контракту | Terra medium | Сверка данных, тест прав доступа, визуальная проверка PDF |
| Доменные доли, ограничения, покрытия РО, repair | Sol high | Контрпример, регрессия на разных профилях, предметное сравнение |
| Очередь, cancel/retry/fencing, атомарное сохранение | Sol high | Несколько реальных PostgreSQL-соединений и fault injection |
| Большой рефакторинг с несколькими зависимостями | Sol high | Characterization до/после и независимое ревью |
| Измерение производительности по готовому сценарию | Terra medium; Sol high для причины | Один и тот же frozen benchmark, все попытки |
| Финальная оценка архитектуры/сложного диффа | Astra high точечно | Сверка с acceptance-критериями; не заменяет эксперта-методиста |

Effort модели, которой пишется код, не ускоряет рабочую генерацию Curriculum-KAG. В системе отдельно используются SBERT/SQL/solver и вызовы LLM; их настройка — другая задача.

## 2. Правила для каждой задачи

1. Начать с текущего кода и воспроизведения указанного дефекта. Историческое passed не засчитывать за текущий runtime.
2. Менять одну границу ответственности. Чужие незакоммиченные изменения сохранить. Не переустанавливать Docker и не менять данные ради зелёного теста.
3. Не ослаблять verifier, не подменять evidence score, не повышать пользовательские лимиты и не добавлять исключения по project_id/названию программы.
4. Использовать существующие модули и формы; новое состояние/поле вводить с явной схемой и миграцией. Не добавлять набор флагов без описанной политики.
5. Для исправления нужна проверка поведения, которое было сломано. Старый тест, повторяющий заглушку реализации, не является доказательством.
6. Заканчивать отчётом: причина, изменённые файлы, команды/exit codes, фактический результат, оставшиеся ограничения. Сохранять run_id, версии кода/модели/данных. Все финальные цифры привязывать к артефакту.
7. Fault injection и массовые генерации выполнять в изолированной PostgreSQL-базе/копии каталога. Runtime-проверка не должна портить действующие проекты и каталог.

## M03 · Доказать надёжность запуска и сохранения

**Приоритет:** до публичной очереди. **Модель:** Sol high. **Старый аудит:** T03–T06, T15.

Контекст: `planner_build.py`, `planner_state.py`, `planner_build_job.py`, `program_spec_snapshot.py`, `run_planner_build_worker.py`, текущий frontend build controller.

1. Различать новый build и повтор старой попытки. Новый запрос после изменения условий получает новый frozen ProgramSpec; retry использует зафиксированный запрос либо явно создаёт новый build.
2. Проверять variants до дорогой синхронизации и постановки в очередь: недопустимые/пустые значения дают 422; не отбрасывать опечатки молча. Нормализация и request hash используют один контракт.
3. Публикация проверяет job_id, owner/fence, отмену и актуальный snapshot в той же транзакции/атомарной операции, которая делает план доступным. Устаревший owner не публикует план даже если ранее прошёл Python-проверку.
4. Реально отменять долгие вычисления на безопасных checkpoints, включая repair/solver. Heartbeat и абсолютный deadline — разные механизмы. Не изменять прежний план при отмене/падении/отказе.
5. Сохранять run-scoped evidence и причины выбора. Успешная публикация MatchScore отдельно от плана не должна лишать старый план своих объяснений.
6. Интерфейс после reload показывает тот же job, выбранный вариант и его результат; повтор клика/сети не создаёт дубликат. Успешный расчёт, отказ ограничений и инфраструктурная ошибка имеют разные сообщения.

**Приёмка на изолированном PostgreSQL:** double-click/тот же Idempotency-Key; другой payload с тем же key; cancel queued; cancel внутри scoring/solver; timeout; остановка worker в ходе build и restart; retry после отказа; старый worker дописывает после нового; два пользователя и два worker; падение между commit плана и записью complete; изменение ProgramSpec во время расчёта. Для каждого: timeline, конечный job state, plan_id, attempt/fence, отсутствие двойной/поздней публикации. Project15-A E2E: новый plan_id сохранён, страницу можно обновить и экспортировать именно его. Длительный live-run здесь обязателен.

## M04 · Получать полезный черновик при конфликтующих требованиях

**Приоритет:** основной продуктовый блок. **Модель:** Sol high для контракта/backend; Terra medium для UI. **Зависимости:** M01, M03.

Не вводить одну галочку «не учитывать ограничения». Ввести два понятных режима:

- **Проверенный план:** все обязательные ограничения выбранного профиля соблюдены; независимое экспертное утверждение отображается отдельным статусом.
- **Рабочий черновик:** максимально полезная найденная заготовка плюс явный список пробелов, отклонений, неопределённостей и следующих действий. Сохраняется отдельно от активного проверенного плана.

Отдельные оси состояния: job_state (queued/running/complete/failed/cancelled/timed_out), result_kind (validated/draft/diagnostic), review_state (unreviewed/reviewed/approved). Черновик может быть успешно вычислен, но не прошедшим предметную проверку. Названия примерные: расширить существующую схему последовательно.

| Настройка в UI | Допустимое поведение |
|---|---|
| «Построить только A» | По умолчанию быстрый первый вариант; B/C отдельным запросом |
| «Предложить новые дисциплины» + лимит | Только proposals с темами/РО/оцениванием/источниками либо явной нехваткой источников; не создавать фиктивно одобренные курсы |
| «Разрешить изменение предпочтительных семестров» | Менять пожелания с показом причин; обязательные зависимости проверяются отдельно |
| «Предложить изменение долей направлений» | Показать исходные/предлагаемые значения и последствия; применять только после согласия и новой версии условий |
| «Показать черновик с непокрытыми РО» | Отобразить непокрытые РО и незаполненные места, не менять score и не писать coverage=100% |
| «Сначала показать готовый вариант» | Явно изменить прежнюю атомарность набора: каждый результат связан с общим run, остальные имеют собственный outcome; не выдавать одну A за три варианта |

Предложения по total credits, нормативным компонентам и обязательным пререквизитам не маскировать как соблюдение. В диагностическом черновике можно показать их дефицит/конфликт, но нельзя активировать такой результат как проверенный. Доступ, валидность данных, согласованность версий и происхождение evidence всегда обязательны. Утверждённые вузом/нормативные ограничения отличаются от пользовательских предпочтений по явному источнику.

Сделать preflight до дорогого solver: понятность/измеримость РО; достаточность кандидатов по каждому критическому РО и домену; кредиты доступных курсов с исключением дублей; обязательные компоненты; грубая совместимость семестров/пререквизитов. Низкий candidate recall отделять от настоящей невозможности: ограниченный shortlist не доказывает отсутствие курсов во всей базе.

Выдавать «нужны ещё 13 кредитов домена 2, доступны такие кандидаты/варианты изменения» вместо raw JSON. Числа считать из текущего run. Если solver исчерпал бюджет, писать «не найдено за выделенное время», а не «доказано невозможно». Не обещать минимальный набор конфликтов, если нет соответствующего алгоритма/сертификата.

**Приёмка:** заведомо несовместимый запрос даёт полезный diagnostic/draft; исходные условия видны; применённое ослабление записано; обязательная проверка не получает ложный passed; cancelled/infrastructure-failed не становятся ready-draft; старый активный план остаётся доступен. Найденный черновик сохраняется независимо от rollback отвергнутой попытки, без случайной публикации рабочих ORM-объектов.

## M06 · Ускорить измеряемые этапы

**Приоритет:** до открытия массовой очереди. **Модель:** Terra medium для измерений, Sol high для изменений. **Старый аудит:** T11–T13; M01 должен быть исправлен.

Есть реальные свидетельства 135–227 секунд успешного build и отказа за 778,549 секунды с 125 684 SQL-запросами. Они неоднородны. Старые 13 секунд — прямой scheduler на подготовленных данных; не использовать это как обещание пользователю.

1. Общий trace: run_id, входной hash, модель/checksum/device, catalog revision, queue wait, model load, evidence/scoring, каждый variant, каждый repair, SQL count/time, publication, ответ/отображение UI, outcome. Error/rejected/cancelled тоже имеют финальное событие.
2. Сначала 3 cold + 3 warm запуска на bachelor/master/doctorate: A отдельно и ABC отдельно. Не вычислять уверенный p95 по трём запускам: это поиск bottleneck. Финальный повторный benchmark — минимум 30 warm наблюдений на фиксированном supported-наборе, с размерами групп и оговоркой о малой выборке.
3. Профилировать повторные ORM-запросы и `_table_stamp/_content_digest` в `planner_stage_cache.py`. Предзагрузить course/LO/evidence/prerequisite/localization в один CandidateContext, переиспользовать в вариантах. Подтвердить улучшение SQL plan/trace, а не только уменьшение строк кода.
4. Persistent embeddings только для реально отсутствующих текстов; ключ включает содержимое модели, preprocessing, язык и текст. Смена checkpoint без смены имени обязана инвалидировать кеш. Не смешивать feature-hash и SBERT.
5. Постоянный ограниченный worker с прогретой моделью. Для одной RTX4050 начать с одного тяжёлого вычисления; сколько выдержит сервер, определить нагрузочным тестом. Три параллельных GPU-процесса автоматически не ускорят очередь.
6. Ограничить повторные repairs: измеримый objective, бюджет, cycle detection, сохранение лучшего допустимого состояния. Добавлять checkpoints отмены. NSGA-II оптимизировать только если trace подтверждает его участие в данном профиле.
7. Страницы: измерить большие payload/долгие query; краткое расписание грузить первым, descriptions/why_selected/граф по запросу. Существующие include-флаги использовать. Не грузить весь каталог в браузер.

**Приёмка:** before/after на одинаковых входах и runtime, контроль качества не ухудшен, причины cache miss записаны, новый frontend видит прогресс без ложных процентов. Предлагаемые бюджеты: enqueue p95 ≤2 с, warm A ≤180 с, warm ABC ≤300 с, основные готовые страницы ≤2 с на agreed test network. Если не достигнуто — отчёт bottleneck и реалистичный SLO, без повышения timeout как «ускорения».

## M07 · Один снимок плана и доказательства объяснений

**Приоритет:** основа корректного PDF и истории. **Модель:** Sol high. **Зависимости:** M02–M05.

Создать общий сериализуемый PlanSnapshot/BuildResult с schema_version: frozen ProgramSpec, plan/run/variant IDs, revisions каталога/модели/правил, items (включая credits, prerequisites и названия), verifier result, исходные/применённые constraints, экспертные решения и source references. Сборка API-DTO, PDF, XLSX и LLM-пакета читает один снимок.

У каждого item хранить reason codes и evidence: какие РО/темы поддерживает; реальный источник; почему допущен; почему этот семестр; обязательные предшественники; влияние на нагрузку; что неизвестно. Для relocation/repair сохранять исходный и новый семестр и правило изменения. Объяснение не должно быть выдуманным постфактум оправданием.

Текущие `why_selected`/semester-insight использовать как представления над snapshot. LLM разрешено перефразировать факты; дополнения/предположения маркировать отдельно. Если нет записи причин у legacy плана, писать «объяснение реконструировано», а не приписывать историческому solver новые основания.

**Приёмка:** изменение Course/MatchScore/Project после сборки не меняет исторический экспорт; нормативные ссылки и evidence относятся к указанной ревизии; сумма и семестры совпадают между UI/XLSX/PDF/JSON; нет возможности запросить чужой snapshot.

## M08 · PDF + промпт для внешней LLM

**Приоритет:** до открытой beta. **Модель:** Terra medium, Sol high на ревью источника данных. **Зависимости:** M02, M07.

Полный контракт и готовый промпт: [08_PDF_AND_LLM_HANDOFF_RU.md](08_PDF_AND_LLM_HANDOFF_RU.md). Реализовать по нему пакет выбранного результата и автоматическую подготовку PDF после завершения расчёта. Экспорт должен также работать по кнопке для исторических планов и отдельно помеченных черновиков. Не вызывать LLM для каждой дисциплины на критическом пути генерации ради PDF.

**Приёмка:** PDF содержит выделяемый русский/казахский текст, полные таблицы без обрезаний, стабильные ID, explanations, нарушения и промпт в этом же документе. После ошибки renderer сам план остаётся доступен, PDF можно повторить. В пакете нет глобальных логов и секретов. Визуальная проверка длинной программы обязательна.

## M09 · Доказать полезность на 20 программах

**Приоритет:** главный gate для заявления «основа для методиста». **Модель:** Terra medium для runner; Sol high для разбора дефектов. **Зависимости:** M01–M08. **Старый аудит:** T17/T18.

1. Взять `program_briefs_20.json`, `04_PROGRAMS_20_RU.md`, протокол `03_ACCEPTANCE_PROTOCOL_RU.md`. Проверить смысловое разнообразие до запуска, совместимость целей/РО/направлений и заявленную поддержку профилей.
2. Сохранить старый обязательный объём приёмки: 20 входов и A/B/C — до 60 проверяемых вариантов. Новый быстрый A-сценарий измерять отдельно. Если beta выпускается A-only, явно зафиксировать сужение продуктового охвата; не засчитывать 20 A за прежние 60 вариантов.
3. Запускать через пользовательский API и persistent worker на неизменяемом снимке БД, не через один scheduler. Все attempts, timeout, rejected и изменения условий остаются в отчёте. Нельзя исключать неудачные кейсы задним числом.
4. Два реально независимых рецензента: предметный и методический; для областей вне их компетенции привлечь профильного. Подготовить обезличенные пакеты существующими `prepare_expert_rubric_packets.py` и формами. Не выдавать две LLM за двух экспертов.
5. Оценить релевантность цели, полноту базовых тем, сложность уровня, последовательность, валидность оценивания, реализуемость нагрузки/практик. Сохранить первичные решения, разногласия и итог.
6. Измерить время методиста от брифа до приемлемой версии, число замен и долю принятых предложений. Для «ускоряет работу» провести сравнение с привычным способом на сопоставимых задачах, учитывая опыт и обучение пользователя; среднее время генерации не равно сэкономленному времени.

**Приёмка:** полный manifest, пакет исходных/итоговых программ, независимые формы, таблица исходов и явный список supported/unsupported профилей. Цифры успеха выводятся из этих файлов. Если эксперты ещё не ответили — статус expert_review_pending, без выдуманного процента завершённости.

## M10 · Подготовить открытый сервис и эксплуатацию

**Приоритет:** до регистрации всех желающих. **Модель:** Sol high для конфигурации/доступа, Terra medium для onboarding. **Зависимости:** M02, M03, M06, M09; M12.

Не требуется новая сложная инфраструктура: управляемый backend + PostgreSQL + ограниченный worker + frontend достаточно. Устранить зависимость доступности от Windows-ноутбука. Production runtime зафиксировать: сейчас compose по умолчанию `ENABLE_SBERT=false`, а успешные локальные измерения часто CUDA; сервер должен либо повторять проверенную модель, либо пройти собственную приёмку качества и времени.

Добавить/подтвердить: HTTPS, изоляцию проектов, пользовательские роли и recovery учётной записи, ограничения активных задач/размера ввода/частоты и fair queue; мониторинг ошибок и очереди; поддержку и понятное сообщение при недоступности; backup и восстановление; описание обработки/удаления данных; право распространять карточки/тексты каталога и учебные материалы; согласие на передачу содержания внешней LLM. Проверить имеющиеся механизмы перед созданием новых. Экспериментальные training/smoke endpoints недоступны обычному методисту.

**Приёмка:** два пользователя не видят данные друг друга, включая экспорт; 5 одновременных запросов заканчиваются управляемыми статусами в capacity-тесте; нагрузка не запускает неограниченные процессы; restart восстанавливает очередь; есть release manifest, проверка health и rollback. Начать с ограниченного supported-набора и постепенно расширять после измерений.

## M11 · Закончить смысловой рефакторинг

**Приоритет:** параллельно стабилизации, не косметический блокер пилота. **Модель:** Sol high. **Старый аудит:** T14.

Не делить по каждые 200 строк и не создавать циклические imports/пачку обёрток ради прежних monkeypatch-тестов. Целевые границы: BuildService → CandidateContext/EvidenceMatrix → VariantStrategy → ScheduleSolver/RepairCoordinator → read-only Verifier → AtomicPublisher → ResultAssembler.

Первыми выделить независимые части из `scheduler.py`: сборку semester evidence/DTO, сохранение Plan/PlanItem и финальный аудит; затем подготовку selection context из `variant_strategy.py`. У этапа явные входы/выходы и состояние, зависимые callbacks создаются после готовности контекста. Pure слой не читает ORM и не commit. Убрать повторные сканы/repair с доказанно одинаковой функцией, сравнивая результат.

Отдельно убрать дубли времени/процессных правил из `epvo.py` и `epvo_process_control.py`: сейчас вынос оставил часть политики в адаптерах. Уточнить UTC-разбор времени, live process identity/create time; проверять фактическую идентичность процесса, а не только сохранённую строку command. Не менять такие правила для прохождения mock-теста.

**Приёмка:** Characterization на профилях до/после, одни правила доменов/кредитов/допуска, отсутствие скрытых commit/cycles, ограниченное число repair и проверка инвариантов после каждой реальной мутации, сравнение времени/SQL. Число строк фиксируется как справка. Файл в 999 строк не закрывает архитектурную задачу автоматически.

## M12 · Собрать единый отчёт данных и восстановления

**Приоритет:** до release; можно параллельно остальным. **Модель:** Terra medium, Sol high при фактическом расхождении. **Старый аудит:** T16.

Исходники доказательств: `.runtime/sqlite-postgres-compare-20260911.json`, `.runtime/sqlite-postgres-derived-compare-20260911.json`, `.runtime/embedding-tolerance-20260911.json`, orphan/discard manifest и журнал restore. Пользователь работает на PostgreSQL; не возвращать приложение на SQLite ради этой задачи. SQLite здесь только исторический источник сравнения.

Составить единый manifest: snapshot IDs/hashes, все таблицы, FK, реальные исключённые строки/причины, exact/hash для авторитетных данных и отдельно утверждённый tolerance для derived embeddings. Не менять `passed=false` вручную: итог пересчитать из проверяемых критериев. Не считать допустимым любое расхождение в embedding, только проверенные строки/размерности/model provenance.

Повторить restore свежего release-backup в изолированную PostgreSQL и сверить таблицы/критичные данные/миграции; сохранить исходный backup и отчёт. Если старое доказательство лежит на E, сначала найти и проверить его, не создавать дубль гигабайтовых копий без необходимости.

**Приёмка:** один понятный отчёт exact/tolerant/excluded/failed, нет необъяснённых потерь, restore подтверждён для выбранного backup и release-профиля. Переезд на PostgreSQL не является причиной удалять legacy источник до закрытия доказательств.

## 3. Порядок выполнения

1. M01 и M02 — конкретные обнаруженные дефекты.
2. M03 — успешный пользовательский A и надёжная публикация.
3. M04–M05 — полезный черновик, объяснимые ограничения, методическая доработка.
4. M06 — скорость по измерениям; подготовительную телеметрию можно делать раньше параллельно M01.

7. M10 — открытая beta после прохождения gate; M12 вести параллельно и завершить до release.

Не нужны новые публичные обещания, пока нет соответствующего acceptance. Если в ограниченном пилоте методист стабильно получает хорошую основу и экономит время, продукт уже полезен — даже до полной автоматизации вузовского утверждения.
