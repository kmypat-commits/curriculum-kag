# Curriculum-KAG: готовность для методистов и решение о запуске

Дата проверки: 13 сентября 2026. Это повторная оценка `01_SENIOR_AUDIT_RU.md`, текущего локального кода и сохранённых результатов. Приложение и рабочая БД не изменялись. Проверка PostgreSQL выполнена в read-only транзакции. Выводы не переносятся автоматически на GitHub/Vercel/production.

## 1. Решение для владельца

**Основное по старому аудиту сделано частично. Открывать сейчас неограниченную генерацию для всех желающих я не рекомендую. Подготовить ограниченный пилот для методистов — разумный следующий шаг.** Позиционирование: «помощник по подготовке и проверке проекта образовательной программы». Результат предназначен для профессиональной доработки и рассмотрения вузом.

Пользователь действительно оценивает полезность результата, а не длину файлов. Поэтому приоритет — получить содержательно подходящий план, объяснить его выбор, сохранить результат, дать возможность исправить его и выгрузить. Полный косметический рефакторинг не должен задерживать пилот. Но дефекты в выборе дисциплин, изоляции пользователей и сохранении влияют непосредственно на этот результат.

У продукта уже есть существенная основа: база дисциплин ЕПВО, сопоставление с РО, планирование по семестрам, проверка кредитов и пререквизитов, версии, отдельный worker, интерфейс обратной связи, черновики силлабусов. Это серьёзная интеграция для одного разработчика. Надёжность и методическая пригодность всех поддерживаемых профилей пока не доказаны.

**Что можно обещать:** подготовку основы плана, поиск подходящих дисциплин, выявление пробелов, объяснения на основе данных и помощь в доработке.

**Что пока нельзя считать доказанным:** готовая к внедрению программа для любого направления, гарантированное соблюдение всех норм, повышение результатов обучения студентов, стабильная генерация за 13 секунд, полная приёмка 20 программ независимыми экспертами.

Исправляю прежний отчёт в переписке: объявление полной цели закрытой было преждевременным. В коде остаются крупные функции; прямой запуск scheduler с rollback не доказывает публикацию через API. Это заключение основано на повторной проверке, а не на прежней отметке «complete».

## 3. Сверка основного со старым аудитом

Статус «частично» означает: полезная реализация есть, но оставшаяся граница явно указана. Не требуется заново переписывать готовые части.

| Задачи старого аудита | Фактический статус | Что осталось для запуска |
|---|---|---|
| T01–T02: честный QA-runner и фикстуры | Реализованы run/attempt, проверки отчётов, stale reconciliation и тесты; есть 20 брифов | Полный актуальный запуск изолированного набора через тот же API/worker, что у пользователя; не только прямой scheduler |
| T03–T04: очередь, cancel/retry/fencing/deadline | Есть durable jobs/attempts, daemon, owner token, heartbeat, deadline, contract tests; в журнале есть частичные runtime-проверки | Проверить отмену внутри долгого этапа, реальный restart, позднюю публикацию старой попытки, replay и конкурентных пользователей |
| T05: снимок входа | `program_spec_snapshot.py`, hash и проверка перед build есть | Генерация и объяснения должны использовать один frozen input до публикации; сейчас scheduler читает mutable Project, а model/catalog revisions не образуют полный immutable run |
| T06: сохранение результата | Старые планы удаляются только после проверки; scoring заменяет scores после расчёта | Доказать атомарность при cancel/retry и раздельность evidence разных запусков. Отдельный commit scores не равен атомарности всего build |
| T07: новые дисциплины/bridge | Лимит уже уважает запрос; core учитывается; незаверенный bridge не закрывает строгий LO-gate | Предметное содержание, подтверждающий эксперт и источники должны быть проверяемы; признак approved сам по себе не методическая экспертиза |
| T08: домены | Ошибка короткого alias исправлялась, выделены scope/policy modules | Найден новый дефект привязки scope-словарей, см. R01. Нужен один согласованный контракт доменных долей |

| T10: verifier и варианты | Есть общий fingerprint, финальные gates и объяснение отказов | Отдельная содержательная оценка, различие похожих вариантов, понятный частичный результат. Сейчас один плохой запрошенный вариант отклоняет весь набор |
| T11–T13: скорость/модель/cache | CUDA подтверждена в ряде запусков; есть кеши, batch-подготовка, телеметрия | Свежие cold/warm замеры, время очереди/UI, дорогие SQL, общий CandidateContext; соответствие production runtime локальному |

## 4. Новые конкретные дефекты и пробелы

### R01. Доменные доли теряются после загрузки ЕПВО — исправить первым

В `backend/app/planner/variant_strategy.py:270` partial-функции получают первоначально пустые `epvo_domain_index` и `epvo_domain_shares`. На строках 327–328 переменные заменяются словарями из `scope_index`. Созданный partial сохраняет ссылки на старые словари. Контрольный пример с текущими policy-функциями: получено 0 вместо ожидаемых 0,75 кредита на единицу.

Это подтверждённый дефект привязки зависимостей; он может неверно считать квоты для записей, которым нужна mapping/evidence, а не прямое совпадение названия домена. Это НЕ доказательство единственной причины каждого отказа, включая последний failed проекта 15. Исправление и интеграционный тест — отдельное первое задание.

### R02. Экспорт не готов к пользовательскому распространению

`backend/app/api/export_api.py`:

- строка 50: только XLSX, полноценного PDF-пакета программы нет;
- выбор `variant_type == A` с `.first()` вместо явного plan_id/выбранного варианта;
- строки 100/111: кредиты берутся из Course/BridgeModule, хотя у PlanItem есть сохранённые credits;
- строка 143: dict/list из metrics_json напрямую передаётся в openpyxl. Изолированно воспроизведён ValueError. В текущих сохранённых планах есть вложенные optimizer/international_quality/verification;
- строка 161: в лист Audit Log выбираются последние 200 событий всей системы без фильтра проекта/владельца. Это риск раскрытия чужих данных, если формирование файла дойдёт до этого участка. Сам факт утечки файлом в текущем сеансе не воспроизводился;
- много запросов внутри циклов Course/LO; полный граф/runtime не должен попадать в обычный методический пакет по умолчанию.

Исправить базовый экспорт, изоляцию и источник данных до добавления PDF. Иначе красивый документ будет противоречить плану или не сформируется.

### R03. Повторная сборка и публикация требуют runtime-доказательства

В `planner_build.py:480` снимок берётся из previous_status либо из нового запроса: отдельно проверить, что новый логический build после изменения условий не наследует старый ProgramSpec. В `planner_state.py:154` проверка owner выполняется до отдельной транзакции обновления; в `planner_build.py:783–784` проверка отмены и commit раздельны. Эти места требуют теста гонки с двумя соединениями PostgreSQL и проверки атомарного fence при публикации. Простая предварительная проверка в Python не доказывает защиту commit от позднего старого worker.

### R04. «Результат не опубликован» слишком часто означает потерю полезной заготовки

В `planner_build.py` любой rejected variant приводит к отказу всего запрошенного набора. Это защищает текущую атомарную публикацию, но не решает задачу методиста получить хотя бы основу. Нужен явный продуктовый контракт: отдельный сохранённый черновик; полный отчёт нарушений; по согласованному режиму — валидный A раньше остальных. Случайную SQL-ошибку или отмену нельзя показывать как «ограничения невыполнимы».

### R05. Объяснения и силлабусы уже частично есть — объединить их

Есть `planner_coverage.py` с `why_selected` и `plan_requisites`, `planner_graph.py:609` с semester-insight, `planner_syllabus.py` с черновиками и DOCX. Не нужно строить ещё три конкурирующих механизма. Но текущие объяснения читают живые Course/MatchScore; это не неизменяемая запись причин решения solver. Нужны сохранённые причины выбора/размещения и единый экспортный снимок.

## 5. Что нужно методисту для полезной основы

Полезный результат — это не только список дисциплин на 240 кредитов. Для каждой критической компетенции должны быть видны темы, дисциплины, место в последовательности освоения и проверяемая работа студента. Отдельно показать практики/исследовательскую работу, междисциплинарную интеграцию, смысловые дубли, нехватку подтверждений и предлагаемые новые дисциплины.

Минимальная карточка дисциплины: название, описание, роль в программе, кредиты, семестр, входные знания, какие РО она поддерживает и на каком основании, пример оценивания, источник/дата/статус содержания. Описания и оценочные задания, предложенные AI, маркировать как проекты для проверки.

Нужен простой цикл доработки: заменить дисциплину из нескольких релевантных кандидатов; зафиксировать одобренную; переместить семестр с повторной проверкой; исправить LO/ограничение; сохранить новую версию; видеть разницу. Отрицательное экспертное решение должно исключать конкретную неподходящую связь, а не становиться общим снижением порога для всех.

Для вузовского внедрения сверх такого фундамента нужны профильный учебно-методический состав, условия реализации, оценочные материалы, практики/ресурсы и утверждение вуза. Правила должны соответствовать выбранной юрисдикции, уровню, актуальной редакции норм и локальным правилам вуза. В этом документе не устанавливаются юридические нормы и не выдаётся подтверждение аккредитации; потребуется реестр источников и проверка ответственным методистом.

Система полезна, если сокращает время до качественного проекта, даже когда нуждается в доработке. Измерять следует **полное время до пригодного проекта с правками**, долю принятых дисциплин, число серьёзных замен и независимую оценку. Similarity/coverage — внутренние индексы поддержки РО, а не вероятность освоения студентом или доказанное улучшение обучения.

## 6. При каких условиях открывать доступ

### Ограниченный пилот

Предложение: 5–10 приглашённых методистов, несколько заявленных поддерживаемых профилей, прозрачный статус beta. До приглашения исправить R01/R02, подтвердить полный цикл A для 15 и минимум двух новых проектов, ввести очередь/квоты, проверить изоляцию двух пользователей и восстановление backup. Уметь показать диагностический отчёт при отказе и скачать корректный план.

### Открытая beta для всех желающих

Перед снятием приглашений выполнить задачи M01–M10 из следующего файла, включая сценарии с параллельными запросами, PDF и проверку 20 программ. Разрешено начать с ограниченного перечня уровней/направлений; для остальных явно сообщать отсутствие доказанной поддержки. Демо и реальные сборки маркировать раздельно. Рабочая генерация должна идти на управляемом сервере/worker с тем же проверенным model profile, а не зависеть от включённого ноутбука.

Предлагаемые критерии приёмки, которые нужно зафиксировать ДО финального прогона (не достигнутые показатели):

- 20 разных брифов: для каждого есть конечный результат и полное объяснение; инфраструктурных зависаний/500 нет. На намеренно конфликтных входах допускается правильный отказ/черновик, а не притворный успех.
- На заранее согласованных выполнимых supported cases строгий A проходит все обязательные проверки; не исключать неудачные случаи после просмотра результата. Если поддержка профиля сужается, это явное изменение релизного охвата.
- Как продуктовый ориентир: минимум 16/20 основ признаны обоими независимыми специалистами полезными для доработки; нет критического содержательного veto среди выдаваемых «проверенных» результатов. Зафиксировать размер и состав выборки, не распространять цифру на все направления.
- Время полного пути и p95 отдельно для cold/warm, A/ABC и очереди. Цель для warm A: p95 ≤180 с, для warm ABC ≤300 с на зафиксированном hardware/model/data. Это ориентиры для измерения, не гарантия текущей версии.
- Ноль случаев доступа к чужому плану/экспорту, двойной публикации и публикации отменённой/устаревшей попытки в приёмочных сценариях.
- PDF/JSON соответствуют одному snapshot; ошибки PDF не уничтожают готовый план; пользователь может повторить экспорт.

Не нужно перед этим переписывать весь стек, строить микросервисы или добиваться идеальных файлов. Сначала закрыть продуктовые риски и предъявить доказательства полезности.
