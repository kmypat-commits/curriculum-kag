# Протокол проверки 20 программ следующей моделью

Статус: **подготовлено к будущему исполнению; новые генерации и экспертные оценки не выполнены**. Набор входов находится в `04_PROGRAMS_20_RU.md`. Все предполагаемые результаты в этом документе — критерии приёмки, а не измеренные показатели системы.

Для автоматизации предоставлен `program_briefs_20.json`: те же 20 брифов и 100 LO, извлечённые из Markdown с проверкой состава. Это **не готовый API payload**: executor должен разрешить реальные scope codes и действующую схему запроса, зафиксировав её без изменения смысла. У всех кейсов исходный execution_status=not_run.

## 1. Что именно проверяем

Гипотеза продукта: из осмысленной цели и явно заданных результатов обучения система создаёт релевантный проект ОП, для которого можно объяснить выбор дисциплин, последовательность, кредиты и способ оценки достижения LO. Отдельно проверяем техническую устойчивость и скорость. Готовность вузу не выводим только из суммы кредитов, индекса similarity или HTTP-кода.

20 входов включают 8 бакалаврских, 8 магистерских (6 научно-педагогических, 2 профильных), 4 докторских; RU/KK/EN; обычные и междисциплинарные программы; несколько областей вне ICT. Ожидаемые варианты A/B/C дают 60 результатов для проверки. Если реализованы не все профили, итог честно указывает покрытие, а не заменяет неподдержанное направление знакомым ICT-профилем.

## 2. Условия старта

1. Исправлен QA-runner T01; известные нарушения T03–T10, влияющие на результат, закрыты или запуск явно помечен диагностическим, не acceptance.
2. Подготовлены изолированные PostgreSQL database/schema и каталог фиксированной revision. Тестовый account создаёт проекты через пользовательский API. Реальные пользовательские проекты/approvals/feedback не изменяются.
3. Сохранены code SHA + dirty patch/hash, model/content/version/config, preprocessing, dataset/ruleset revision, Python/packages/OS, CPU/GPU/RAM, actual device и actual model mode. Никаких секретов в пакете.
4. Методист подтверждает применимость поддерживаемого профиля объёма к выбранному направлению. Числа 240/8, 120/4, 60/2, 90/3, 180/6 в брифах взяты из возможностей приложения, не являются универсальным нормативным заключением.
5. Разрешить реальный code/group/direction через каталог ЕПВО для нужного уровня. Записать выбранные значения, названия и rationale в input. Не изобретать коды; не использовать B057/M094/D094 для всех программ. Если нужного scope нет — `unsupported_scope`, остановить этот кейс и сохранить пробел.
6. Сначала 2 smoke-кейса, затем остальные последовательно при concurrency=1. Hardware benchmark и проверку concurrency проводить отдельно, не смешивать с контентной когортой.

## 3. Как готовить вход

Брифы содержат точные цели и пять проверяемых LO. Они не равны полному обязательному нормативному набору: предусмотренные профилем нормативные результаты/компоненты можно добавить как отдельный regulatory слой, сохранив исходные пять профессиональных LO.

Для каждого кейса создать immutable `input.json`: case_id, title, verbatim_goal, verbatim_los, level/track, target_language, program_type, scope с кодами, credits/semesters, constraints, bridge_limit, required_topic_blocks, prerequisite_expectations, prohibited_substitutions, evidence requirements и reviewers rubric version. LO не заменять универсальными IT-формулировками. Перевод допустим только с сохранением смысла и отдельной записью source/translated text до начала запуска.

Все LO по умолчанию weight=1.0. До просмотра результата методист может отдельно пометить критические LO; если не пометил, все пять считаются критическими. Ни один нельзя объявить второстепенным задним числом. Для междисциплинарных программ зафиксировать допустимые квоты областей и базу расчёта до build; бриф не задаёт универсальный закон «50/50». Если API не может выразить ограничение, это feature gap, не причина тихо отбросить требование.

Bridge_limit относится ко всем новым модулям, включая structural core, balance и другие технические префиксы. Если источников хватает, новый модуль не обязателен. `0` означает отсутствие любых generated-дисциплин. При недостатке содержательного evidence честный отказ предпочтительнее неподтверждённого готового плана, но для acceptance такой кейс остаётся непокрытым.

## 4. Выполнение одного кейса

1. Через API создать проект/версию с зафиксированными inputs; сохранить точный request без auth headers. Проверить прочитанный обратно снимок.
2. Запросить A/B/C с устойчивым idempotency key. Проверить job_id и queued/running переходы. Не делать второй build при медленном ответе; повторять тот же transport request с тем же ключом по протоколу.
3. Сохранять telemetry event stream. Polling клиента не чаще 30–60 секунд; не перезапускать генератор ради просмотра статуса. При длительном вычислении ориентироваться на deadline и stage trace, а не секундные опросы. Не создавать новую автоматизацию без отдельного запроса владельца.
4. При успехе получить сохранённые варианты, evidence, graph, syllabus/модули и export через API, затем открыть UI. Прямой результат функции scheduler недостаточен.
5. Запустить самостоятельный read-only verifier на окончательных данных. Повторно считать кредиты из PlanItems; проверить соответствие сохранённым BridgeModule и экспортам после построения всех вариантов.
6. Выполнить предварительную содержательную оценку по каждому LO/блоку/chain. Это ассистентская проверка, не независимый эксперт.
7. Сохранить packet и результат с причинами. При failure сохранить первый неуспех; retry на новой версии кода или данных — новая attempt со ссылкой на прежнюю, не замена истории.

## 5. Артефакты на каждый кейс

Предлагаемый каталог будущих результатов: `D:\curriculum-kag\curriculum-kag\output\acceptance-20\<run-id>\<case-id>\`.

```text
input.json                     исходная цель/LO + разрешённые коды и ограничения
manifest.json                  code/data/model/policy/config/hardware hashes
attempts/<attempt-id>/
  request.json                 пользовательский API request, без секретов
  job-events.jsonl             времена и смены состояний
  performance.json             очередь/cold/scoring/A/B/C/verify/publish/UI
  variants/A.json, B.json, C.json
  evidence.json                course/LO/topic/assessment/source/status
  prerequisites.json           направление, обязательность и происхождение рёбер
  verification-independent.json
  content-review-assistant.md  оценка ассистента, явно не human expert
  screenshots/                минимум overview, disciplines/semesters, graph, LO
  exports/                    пользовательская выгрузка программы
  result.json                 passed/failed/incomplete + blockers + attempt-id
expert-reviews/               только реально заполненные независимые рецензии
```

Все результаты имеют SHA-256 в run manifest. Пакет самодостаточен: нельзя ссылаться только на исчезающий local project-id или красивый screenshot. Не включать личные данные реальных студентов, credentials и сырые auth logs.

## 6. Независимые автоматические gates

| Gate | Требование | Отказ |
|---|---|---|
| INPUT | Цель/LO/уровень/scope/язык/ограничения совпадают со снимком | Тихая подмена входа |
| VOLUME | Общая сумма, нормативные блоки, практика/исследования, семестры и допуски соответствуют конкретному профилю | Недобор/перебор за допуском; скрытая смена credits |
| BRIDGE | Count/credits в лимите; target LO обоснован темами и assessment; proposal ≠ approved | AUTO_BALANCE заявляет все LO без содержания; cap расширен |
| REAL-EVIDENCE | У каждого критического LO есть реалистичный образовательный путь и source-backed содержание; generated-only отмечено для обязательной экспертизы | Similarity/target label выдаётся за доказательство |
| PREREQ | Required missing/cycles/order проверены; все связи имеют источник или hypothesis label | Удаление нужного ребра; safety смешана с cybersecurity |
| RELEVANCE | Обязательные блоки из брифа представлены; список соответствует цели и уровню | Вместо транспорта общий IT; вместо докторантуры базовое введение |
| DEDUP | Дубли оцениваются по темам/работам, не только ID; последовательные courses имеют обоснованную прогрессию | Три названия одной методологии заполняют разные слоты без нового содержания |
| VARIANTS | Три валидных альтернативы с объяснимыми различиями; canonical hash устойчив к порядку | Перестановка items/новые ID выданы за другое содержание |
| CONSISTENCY | DB/API/UI/graph/export совпадают; финальный C не меняет уже проверенный A | Несогласованные credits, предметы или prerequisites |
| JOB | Один результат на idempotency input, terminal outcome, корректные cancel/retry и restart | Вечная очередь, дубли, поздняя публикация cancelled job |
| I18N | RU/KK/EN сохраняют смысл LO/терминов и статусы; fallback явно виден | Raw keys, ложный перевод дисциплины или причин отказа |

Verifier не использует генератор для «допочинки» проверяемого плана. Для adversarial-тестов взять копии valid plan и по одному внести неправильный credit, missing prerequisite, fake bridge evidence, duplicate ID/title, wrong level, order-only variant. Каждый дефект должен обнаруживаться — это проверяет чувствительность самого gate.

## 7. Содержательная оценка и университетская пригодность

Два независимых рецензента получают полные пакеты, исходные цели и rubric **до** просмотра автоскоров. В сумме нужны компетенции в предметной области и проектировании ОП. Для 20 разных областей может понадобиться больше двух людей: два рецензента на каждый кейс, а не любые два человека на все дисциплины. Их имена/квалификацию/конфликт интересов фиксируют с согласия. Отсутствие реальных рецензентов — `expert_review_pending`.

Предлагаемая rubric 0–4 по восьми измерениям:

1. Соответствие цели и профессиональным ролям выпускника.
2. Покрытие всех критических LO содержанием и проверяемыми работами.
3. Полнота ядра и отсутствие нерелевантных/дублирующих дисциплин.
4. Уровень сложности, особенно исследовательская новизна master/doctorate.
5. Логика prerequisite, progression и реалистичность нагрузки.
6. Содержательность и реализуемость новых bridge-модулей.
7. Качество assessment, практик/исследования и итоговой аттестации.
8. Реализуемость вуза: преподаватели, инфраструктура, источники, язык и применимые правила.

Якоря: 0 — отсутствует/противоречит; 1 — существенные провалы; 2 — нужно серьёзно переделать; 3 — пригодно с конкретными исправлениями; 4 — обосновано и связно. Предлагаемый порог для ограниченного пилота: каждый критерий ≥3 у обоих экспертов после разрешения замечаний и отсутствие veto. Это согласуемый порог данного испытания, не национальный стандарт.

Veto независимо от среднего: отсутствует критическая компетенция; нормативно недопустимый объём; педагогически неверная обязательная зависимость; небезопасная профессиональная подготовка; неподтверждённый generated-only путь по критическому LO; отсутствует реальный способ реализации практики/исследования. Для прикладного здравоохранения явно исключить выдачу квалификации врача через ICT-программу.

Рецензенты оценивают независимо, затем фиксируют разногласия и согласованное решение; первоначальные баллы не переписывают. LLM-рецензии — вспомогательное приложение, не два внешних эксперта.

## 8. Скорость и устойчивость: не смешивать с уникальностью

Основные 20 разных кейсов измеряют breadth, но не дают надёжный SLO каждого профиля. Для performance выбрать заранее 5 представителей: P01, P04, P09, P14, P17; после основного cohort сделать по 3 тёплых повтора и отдельный cold run каждого. Повторные runs не считать новыми уникальными программами. Количество можно сократить по бюджету владельца, но тогда явно не объявлять статистический p95 стабильным.

Измерять queue wait, time-to-first-valid-A, all-variants compute, end-to-end UI, retries, failed duration, memory/device. Не исключать неудачи из отчёта доступности. Предлагаемые целевые ориентиры аудита (ещё не достигнутые): enqueue p95 ≤2 с, first valid p95 ≤90 с, warm complete p95 ≤300 с; аппаратная конфигурация фиксирована. Не снижать качество ради времени.

## 9. Итоговый отчёт следующего исполнителя

Для каждой P01–P20: exact input hash; supported/not_supported; generated variants; hard defects; content defects; response/compute time; actual model mode; independent reviewer state; verdict и ссылки на evidence. Общий вывод отдельно по четырём шкалам:

- технически завершено X/20 inputs и Y/60 вариантов;
- прошли independent automatic gates X/20;
- прошли содержательную предварительную проверку X/20;
- одобрены реальными независимыми рецензентами X/20.

Ни один знаменатель не заменять числом удачных повторов. Не округлять неизвестность до 100%. При отсутствии экспертов можно завершить технический аудит, но нельзя подписать готовность для внедрения. Финальное формальное утверждение программы — решение академических органов конкретного вуза.
