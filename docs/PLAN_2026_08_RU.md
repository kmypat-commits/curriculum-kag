# План развития проекта (2026-08)

> **Актуальный инженерный статус на 25.08.2026.** Локальный regression gate: **89/89 backend-тестов**, compile/static/release-hygiene gates и frontend production build проходят. Ranking/assembly/retrieval и semester/domain repair вынесены в отдельные planner-модули; KAG API error boundaries сужены до двух транзакционных границ, а PostgreSQL dump/restore round-trip добавлен в CI. Текущие health/Alembic/endpoint gates на PostgreSQL проходят, HTTP smoke проверяет 10 маршрутов, включая граф, и RU/KK/EN markers; интерактивный graph smoke требует авторизованного сеанса.

Последний честный graded hybrid-benchmark на полном candidate pool: Recall@10=0,6102 для fuzzy train-only anchors (73 test-программы, 561 LO-запрос); он не внедрён, поскольку ниже целевого 0,80. Свежий export восстановлен из raw SQLite EPVO с оценками 0/0,5/1 и историческими 0,25/0,75. Эксперимент использует только train-векторизацию/anchors, поэтому не смешивает test-разметку с обучением. Вес 0,35 выбран по validation (Recall@10=0,5848) и на test дал Recall@10=0,6099, MRR=0,6257; контекст программы как lexical-prior ухудшил Recall@10 до 0,5330 и отклонён.
Полный PostgreSQL export без programme cap теперь содержит 11 017 программ,
833 022 course--LO строк и 615 414 положительных expert-связей
(train/validation/test=7 706/1 650/1 661); он описан в
`docs/EPVO_FULL_DATASET_2026_08_RU.md`. Старый benchmark-срез сохраняется для
сопоставимости. Потоковый полный benchmark уже выполнен: validation Recall@10
0,5832, test Recall@10 0,6098 и MRR 0,6380; SBERT 40k hybrid дал validation
0,5829 и test 0,6137. RU-only вариант поднял validation до 0,5914 и test до
0,6172, но всё ещё ниже целевого 0,80, поэтому production reranker не изменён.
Graded-anchor с непрерывной экспертной силой дал validation Recall@10=0,5814
и также отклонён по главному критерию.
Идентификационный аудит показал 0% точного course--LO overlap между train и
held-out; поэтому запоминание экспертных пар исключено, а следующий reranker
должен обобщать семантику и programme-level признаки.
Title-only fuzzy-anchor проверен отдельно на validation (Recall@10=0,5632) и также не внедрён.
Дополнительно проверены train-only scope-anchor (Recall@10=0,5683), scope-membership
(0,4778) и малый supervised pair-ranker на 300 train-программах/37 700 парах
(0,5485); все варианты хуже fuzzy baseline и оставлены только как журнал
отрицательных экспериментов.
Раздельный RU/KK/EN multilingual-max pilot на 19 validation-программах дал
0,5877 против 0,6648 у fuzzy-варианта и также не внедрён.
CUDA multi-positive pilot (1 000 групп, 500 шагов) дал Recall@10=0,6055 в лучшей смеси, то есть не превзошёл fuzzy baseline 0,6099; production-модель не меняется.
Expert memory по стабильному ID дисциплины (coverage ~41%) дал validation Recall@10=0,5754 и отклонён до test-прогона.

Для latency закрыт первый измеримый bottleneck: после индексов planner read endpoints variants стабильно отвечают за 0,273–0,342 с, graph — за 0,172–0,186 с на PostgreSQL shadow-БД. Повторную полную индексацию EPVO и тяжёлые ML-прогоны для этого изменения не запускали.

В `variant_strategy.py` исправлен недостижимый фильтр общих дисциплин: после
кибер-ветки теперь корректно применяется требование минимального LO-доказательства
 для остальных профессиональных программ. 89/89 тестов и runtime smoke после
перезапуска PostgreSQL проходят.

## Фаза 2. Прод-таргет: Supabase + хостинг бэкенда

**Vercel не подходит для полного стека** (Python+torch/SBERT, 11 GB БД, subprocess-обучение, git-shell вызовы). Честная конфигурация:

- **Supabase = да** — управляемый Postgres 16 + pgvector + auth + storage. Это целевой слой данных и заодно закрывает путаницу 5432/5433 (локальный primary/shadow).
  - Миграция уже возможна: `pg_dump` (backup verified) → импорт в Supabase.
  - Векторы: `pgvector` уже используется (`HAS_PGVECTOR`).
  - Auth: сейчас JWT + OAuth2PasswordRequestForm — при желании переносится на Supabase auth.
- **Backend**: Render / Railway / Fly.io (Docker, `backend/Dockerfile` уже есть) — долгоживущий Python-процесс, подходит. Либо остаётся локальным Docker для исследовательских задач.
- **Frontend**: Vercel/Netlify — только статический демо-слой, при условии выноса тяжёлых операций в API бэкенда.

## Фаза 3. MCP / skills / plugin / хуки (выборочно, не «побольше»)

1. **codebase-memory MCP** — ранее проверялся, но удалён из рабочего запуска из-за двойного процесса и нагрузки. Для текущего рефакторинга достаточно локального поиска и acceptance; возвращать его не планируется без отдельного профиля ресурсов.
2. **GitHub MCP** — работа с PR/issues после выгрузки.
3. **Проектный skill** (`curriculum-kag`): конвенции, команды (`test.ps1`, `acceptance-test.ps1`), структура, где лежит проде-модель.
4. **Хуки**:
    - git pre-commit: `check_text_encoding.py` + `run_tests.py` (сейчас 89/89) — ловит оба известных регресса (кодировка/тесты) до коммита.
   - opencode hook: уведомления о старте/завершении длинных задач.
5. Plugin — только когда понадобится конкретика (например, для интеграции с Supabase).
